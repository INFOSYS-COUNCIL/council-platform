# 정보시스템학과 학생회 운영 플랫폼 기획서 v0.8

> Student Council Operations Platform · Product & Technical Planning  
> 기술 스택: **Next.js · Vercel · Supabase · BlockNote · Yjs**  
> 기준일: **2026-10-29**

이 문서는 정보시스템학과 학생회 운영 플랫폼의 제품 범위, 권한 정책, 데이터 구조, 실시간 공동 편집 방식과 개발 완료 기준을 정의한다. v0.7은 v0.6 검토에서 나온 권한 상속 충돌, 인증 강제 위치, CRDT 저장 경로, 누락된 핵심 스키마와 Term 전환 규칙을 정리해 구현을 시작할 수 있는 수준으로 확정했다. v0.8은 2026-10-29 킥오프에서 회장단과 확정한 운영값과 일정을 반영하고, 본문의 어긋난 부분을 정리하고, 기능별 화면 명세(부록 C)를 추가한다.

TF 작업 방식(역할, 주간 리듬, Git 규칙, 리뷰)은 이 문서가 아니라 `docs/TF_작업방식_기준.md`에서 다룬다.

## 3줄 요약

1. 학생회 내부 계정은 검증된 학교 Google 계정과 사전 승인 정보를 서버에서 연결하며, 학교 도메인 검사는 Supabase Auth Hook에서 강제하고 Role과 Permission은 고정된 보안 규칙으로 계산한다.
2. Event의 열람 범위를 기준으로 자료·일정·인수인계 권한을 상속하고, Task와 회의록은 그 범위 안에서 더 좁은 ACL을 적용한다. 담당자·편집자·ACL 대상은 Event를 열람할 수 있는 사용자만 지정할 수 있다.
3. 회의록은 **BlockNote + Yjs CRDT**로 공동 편집하며, 묶음 단위 Update를 DB 함수가 저장한 뒤 DB에서 Broadcast해 Vercel 왕복 없이 저장 확인·재시도·재접속 동기화를 보장한다.

# 0. 서비스 목표와 설계 원칙

이 플랫폼은 단순한 학생회 홈페이지가 아니라, 학생회 구성원이 업무를 수행하고 기록을 다음 운영진에게 남길 수 있는 **학생회 운영 OS**를 목표로 한다.

핵심 영역은 다음과 같다.

- 조직/구성원 관리
- Dashboard
- Task Tracker
- Event 및 행사 자료
- Meeting Minutes
- Schedule
- Suggestion
- Handover
- Activity Log

## 0.1 설계 원칙

| 원칙 | 적용 방식 |
|---|---|
| 운영 데이터 비하드코딩 | 부서, 직책, 구성원, Dashboard 링크, 회의 Template, 열람 대상 등을 DB에서 관리 |
| 보안은 DB에서 강제 | 화면 숨김만 사용하지 않고 Supabase RLS에서 SELECT/INSERT/UPDATE/DELETE 제한 |
| ACL 기반 열람 제어 | 회의록과 Task에 부서·개인·역할 그룹 단위 접근 규칙 적용. Task는 기본 공개/제한 공개 구분 |
| 읽기와 쓰기 분리 | 회의록 열람, 본문 편집, Realtime 수신·송신, CRDT 저장 권한을 별도로 검증 |
| 저장 확인 후 동기화 | CRDT 업데이트는 영속 저장 성공을 확인하고 전파하며 실패 시 재시도·재동기화 |
| 상위 자원 권한 상속 | Event 자료·일정·인수인계는 Event 열람 범위를 상속하고 하위 ACL이 상위 범위를 넓히지 못하게 함 |
| 권한 규칙 단일화 | Role별 Permission 목록과 범위를 DB 함수에서 계산하고 Frontend·RLS·Realtime이 같은 규칙을 사용 |
| 기록 보존 | 구성원 삭제는 계정 삭제가 아니라 Membership 종료 처리 |
| 완료 Task 수정 허용 | DONE 상태도 수정 및 재오픈 가능, 변경은 Activity Log에 기록 |
| 다음 기수 자동 복제 제외 | Term 개념은 유지하되 이전 기수 데이터 복제 기능은 개발하지 않음 |

# 1. 실제 학생회 조직 구조

## 1.1 초기 조직

```text
학생회
├─ 회장
├─ 부회장
├─ 사무국
│  ├─ 사무국장
│  └─ 국원 N명
├─ 재무국
│  ├─ 재무국장
│  └─ 국원 N명
├─ 홍보국
│  ├─ 홍보국장
│  └─ 국원 N명
└─ 생활복지국
   ├─ 생활복지국장
   └─ 국원 N명
```

위 구조는 **초기 Seed**다. `사무국`, `재무국` 등의 이름을 코드에 고정하지 않는다. 회장단은 관리자 화면에서 부서를 추가·수정·정렬·비활성화할 수 있다.

## 1.2 Role과 Position 분리

| 구분 | 값 예시 | 의미 |
|---|---|---|
| Role | `MEMBER`, `DIRECTOR`, `EXECUTIVE` | 활성 Membership에 저장하는 보안 권한 레벨 |
| Position | 회장, 부회장, 사무국장, 재무국장, 국원 등 | 실제 표시 직책 |
| Department | 사무국, 재무국, 홍보국, 생활복지국 등 | 소속 조직 |

`STUDENT`는 Membership Role이 아니라 활성 Membership이 없는 로그인 사용자의 파생 상태다. Role은 최소 보안 경계이므로 소수의 고정 Enum으로 유지하고, Position/Department는 DB에서 운영자가 관리한다.

문서에서 **회장단**은 `EXECUTIVE` Role, **국장**은 `DIRECTOR` Role, **국원**은 `MEMBER` Role을 뜻한다. 회장·부회장 같은 Position 이름은 설명용 예시이며 권한 판정 기준이 아니다.

Membership 규칙:

- 한 사용자는 한 Term에 활성 Membership을 하나만 가진다(`term_id + user_id` 부분 유일 제약, `is_active=true` 조건).
- `EXECUTIVE`는 `department_id`가 없을 수 있다. `DIRECTOR`와 `MEMBER`는 반드시 같은 Term의 부서에 속한다.
- 한 부서의 활성 `DIRECTOR`는 MVP에서 1명으로 제한한다. 공동 국장이 필요하면 운영값으로 다시 결정한다.

## 1.4 Permission 계산 방식

Permission Key 목록과 Role별 기본 매핑은 마이그레이션으로 관리한다. MVP에서는 관리 화면에서 Role의 보안 권한을 임의 변경하지 않는다. 관리 화면의 `권한` 메뉴는 Role별 권한과 적용 범위를 조회하는 용도로 제공한다.

권한 계산은 다음 입력을 사용한다.

1. 요청 사용자의 같은 Term 활성 Membership과 Role
2. Membership의 Department
3. 대상 자원의 Term, 소유 Department, 생성자, 담당자, 관리자
4. 대상 자원의 공개 모드와 ACL

Frontend는 계산된 Permission으로 버튼을 표시하고, DB 함수는 같은 규칙으로 RLS와 RPC를 판정한다. 보안 함수는 고정 `search_path`를 사용하고 일반 사용자가 직접 수정할 수 없는 스키마에 둔다. Position 이름은 표시 용도이며 권한 판정에 사용하지 않는다.

## 1.5 국장 구성원 관리

국장은 자기 소속 국에 한해 구성원을 추가하거나 제외할 수 있다.

- 추가: `@hanyang.ac.kr` 이메일을 등록하고 `MEMBER` Role로 자기 국에 배정
- 제외: `memberships.left_at` 또는 `is_active=false`로 Membership 종료
- 사용자 Profile과 과거 Task/Event/Meeting 기록은 삭제하지 않음
- 국장이 다른 국 구성원을 수정하거나 `DIRECTOR`, `EXECUTIVE`로 승격하는 것은 불가
- 국장의 추가/제외 요청은 서버의 권한 검사 후 처리하며, 클라이언트가 Role·Term·Department를 임의 지정해 우회할 수 없게 한다
- 국장이 구성원을 추가하면 `approved_council_accounts`에 승인 행을 만들고, 해당 사용자의 첫 로그인 때 2.2절 절차로 Membership이 활성화된다

### 종료된 Membership이 참조된 자원

Membership을 종료해도 과거 기록의 `assignee_id`, `manager_id`, `author_id`, `meeting_editors`는 삭제하지 않는다. 다만 권한 판정은 항상 활성 Membership을 요구하므로 종료된 사용자는 어떤 권한도 행사하지 못한다.

- 종료 화면은 해당 사용자가 담당·관리 중인 미완료 Task, 관리 중인 Event·RESTRICTED Task, 편집자로 지정된 진행 중 회의록 수를 보여 준다.
- 종료하는 사람은 관리 책임(`manager_id`)을 다른 활성 구성원에게 넘기거나, 넘기지 않으면 관리 책임이 소속 국의 활성 국장(없으면 회장단)으로 이동한다.
- Dashboard와 목록은 "담당자 비활성" 표시로 재배정이 필요한 Task를 보여 준다.

## 1.6 ACL 대상 값 정의

Event·Task·Meeting ACL은 같은 대상 형식을 사용한다.

| `subject_type` | 사용 필드 | 의미 |
|---|---|---|
| `ROLE_GROUP` | `role_group` | 아래 역할 그룹 |
| `DEPARTMENT` | `department_id` | 같은 Term 해당 부서의 활성 구성원 전체(국장 포함) |
| `USER` | `user_id` | 같은 Term에 활성 Membership이 있는 특정 사용자 |

| `role_group` | 포함 대상 |
|---|---|
| `ALL_COUNCIL` | 같은 Term의 활성 MEMBER·DIRECTOR·EXECUTIVE 전체 |
| `DIRECTORS` | 같은 Term의 활성 DIRECTOR와 EXECUTIVE |
| `EXECUTIVES` | 같은 Term의 활성 EXECUTIVE |

ACL 테이블에는 `subject_type`에 맞는 필드 하나만 채워지도록 CHECK 제약을 두고, 같은 대상의 중복 규칙은 유일 제약으로 막는다. 대상 부서·사용자의 Term이 자원의 `term_id`와 다르면 저장을 거부한다.

예외: Meeting ACL(`meeting_access_rules`)은 MVP에서 `ROLE_GROUP`·`DEPARTMENT`만 사용하고 `user_id` 필드를 두지 않는다(6.3절). 개인 단위 접근은 생성자·지정 편집자·회장단의 기본 접근으로만 처리한다.

## 1.7 상위 범위 밖 지정 금지

Event에 속한 Task·Meeting에서 다음 지정은 **대상이 해당 Event를 열람할 수 있을 때만** 허용한다.

- Task `assignee_id`, `manager_id`, `task_access_rules`의 `USER`·`DEPARTMENT` 대상
- Meeting `author_id`, `meeting_editors`, `meeting_access_rules`의 `DEPARTMENT` 대상

지정 화면은 Event를 열람할 수 없는 사용자·부서를 선택 목록에서 비활성화하고 이유를 표시한다. Event 관리 권한이 있는 사용자는 같은 화면에서 Event ACL에 대상을 먼저 추가할 수 있다. 서버 RPC도 같은 검사를 수행하며, 검사에 실패하면 저장하지 않는다. 이 규칙으로 "편집 권한이 있는데 열람할 수 없는" 상태와 "ACL에 넣었는데 실제로는 보이지 않는" 상태를 막는다.

회장단, Event 생성자, Event 관리자는 Event 열람자에 항상 포함되므로 별도 검사 없이 지정할 수 있다.

# 2. 학생회 계정 검증 및 로그인

## 2.1 기본 인증

모든 로그인은 Google OAuth를 사용한다. 서버는 Google이 검증한 이메일(`email_verified`)이 `@hanyang.ac.kr`인지 확인한다. 학교 계정이 Google Workspace에 속하는 운영 방식이라면 Google ID Token의 `hd` 클레임도 확인한다. 이메일 문자열의 접미사만으로 Workspace 소속을 단정하지 않는다. 학교의 실제 Google 계정 운영 방식을 배포 전에 확인한다.

### 검사 위치

OAuth 요청의 `hd` 파라미터와 로그인 화면의 안내는 계정 선택 힌트일 뿐 보안 검사가 아니다. 도메인 검사는 다음 두 곳에서 강제한다.

1. **Supabase Auth Hook(Before User Created)**: 검증되지 않은 이메일, 학교 외 도메인, 기대한 `hd`가 없는 계정은 `auth.users` 행이 만들어지기 전에 거부한다. 이 Hook은 Postgres 함수 또는 서명 검증을 하는 HTTP Hook으로 구현한다.
2. **Profile 생성·Membership 활성화 함수**: 같은 조건을 다시 검사해 Hook 설정 누락이나 다른 Provider 추가로 우회되지 않게 한다.

Supabase 프로젝트에서는 Google 외 로그인 Provider(이메일·Magic Link 등)를 비활성화한다. 배포 전 학교 외 Google 계정으로 로그인했을 때 `auth.users`와 `profiles`에 행이 생기지 않는지 확인한다.

"일반 학생"은 검증된 `@hanyang.ac.kr` 계정을 뜻하며 학과 소속은 확인하지 않는다. 학과 학생으로 건의를 제한해야 하면 별도 명단 대조를 운영값으로 결정한다.

일반 학생과 학생회 구성원의 차이는 **로그인 가능 여부가 아니라 내부 Membership 보유 여부**다. 이메일은 사전 승인 대조에 사용하고, 활성화 후 계정 연결의 기본 키는 `auth.users.id`를 사용한다.

```text
@hanyang.ac.kr Google 로그인
        ↓
Supabase Auth
        ↓
profiles 생성/조회
        ↓
approved_council_accounts 확인
        ├─ 등록 없음 → STUDENT
        └─ 등록 있음 → 서버에서 승인 상태·기수·이메일 검증 → Membership 활성화
```

## 2.2 회장단 초기 일괄 등록

기수 시작 전 회장단이 학생회 구성원의 학교 계정을 일괄 입력한다.

`approved_council_accounts` 제안 필드:

| 필드 | 설명 |
|---|---|
| `term_id` | 적용 기수 |
| `email` | 학교 이메일 |
| `department_id` | 배정 국 |
| `role` | MEMBER / DIRECTOR / EXECUTIVE |
| `position_id` | 표시 직책 |
| `registered_by` | 등록한 회장단 사용자 |
| `activated_user_id` | 실제 첫 로그인 후 연결된 auth user |
| `is_active` | 승인 상태 |

이 테이블은 학생회 내부 권한의 **Allowlist** 역할을 한다. 단순히 학교 이메일을 가지고 있다는 이유만으로 학생회 내부 권한을 부여하지 않는다.

활성화 규칙:

- `term_id + 정규화된 email`을 유일하게 관리한다. 이미 연결된 승인 행을 다른 사용자에게 다시 연결하지 않는다.
- 최초 로그인 시 서버 측 단일 절차에서 검증된 계정과 승인 행을 대조하고 `activated_user_id` 연결 및 Membership 생성을 원자적으로 처리한다. 클라이언트가 Role·Department·Position을 직접 쓰지 못한다.
- 승인 취소 또는 Membership 종료 후에는 DB 쓰기와 조회 권한이 즉시 사라지도록 활성 Membership을 매 요청에서 검사한다. Realtime 연결의 권한 회수 지연은 6.6절에서 다룬다.
- 첫 EXECUTIVE는 기존 회장단 권한이 없으므로, 운영자가 검증된 학교 계정을 확인한 뒤 신뢰된 서버 마이그레이션/관리 절차로 한 번만 초기 등록한다. 첫 계정이 자신의 Role을 직접 부여하는 화면은 만들지 않는다.

## 2.3 운영 중 구성원 변경

- 권한 승격(국원→국장, 국장→회장단): 회장단만 가능

# 4. Task Tracker와 열람 ACL

## 4.1 Task 기본 구조

`tasks` 주요 필드:

- `term_id`
- `event_id` (선택. Event에 속하지 않는 부서 업무는 비움)
- `department_id`
- `title`
- `description`
- `creator_id`
- `assignee_id`
- `status`: TODO / IN_PROGRESS / REVIEW / DONE
- `priority`
- `start_date`
- `due_date`
- `completed_at`
- `visibility_mode`: DEFAULT / RESTRICTED
- `manager_id`: 해당 Task의 ACL 관리 책임자
- `created_at`, `updated_at`

DONE은 잠금 상태가 아니다. 권한이 있는 사용자는 완료 후에도 제목·설명·담당자·마감일·자료를 수정하거나 상태를 다시 IN_PROGRESS로 돌릴 수 있다.

## 4.2 Task 공개 모드와 기본 열람 범위

Task 생성 시 `visibility_mode`를 선택한다. 기본값은 `DEFAULT`다.

| 모드 | 열람 대상 |
|---|---|
| `DEFAULT` | 해당 기수 회장단, 담당 국 활성 구성원, 생성자, 담당자, ACL에 추가된 대상 |
| `RESTRICTED` | 해당 기수 회장단, 생성자, 담당자, ACL에 명시된 대상만 |

`RESTRICTED`는 계약·개인정보 등 민감 업무에 사용한다. 담당 국의 다른 구성원과 국장은 자동 열람하지 않는다. 제한 공개로 전환할 때 기존 ACL과 담당자 목록을 미리 보여 주어 의도하지 않은 공개가 남지 않게 한다. 화면에도 회장단·생성자·담당자의 기본 접근을 명시한다.

국원은 두 모드 모두에서 권한이 부여되지 않은 타 부서 Task를 조회하지 못한다. ACL 판단에는 반드시 **Task가 속한 Term의 활성 Membership**만 사용한다.

## 4.3 Task 열람 대상 특별 지정

회장단과 권한이 있는 국장은 Task별로 열람자를 지정할 수 있다. `DEFAULT`에서는 기본 대상에 추가하고, `RESTRICTED`에서는 회장단·생성자·담당자를 제외한 열람자를 명시한다. Event에 속한 Task는 1.7절에 따라 Event를 열람할 수 있는 대상만 지정할 수 있다.

### 지원 대상

- 특정 국 1개 또는 복수 국
- 특정 국원 1명 또는 복수 사용자
- 국과 무관하게 학생회 구성원 N명 직접 선택

예시:

```text
Task: 대동제 업체 계약 검토
기본 담당 국: 재무국
추가 열람:
- 사무국 전체
- 홍보국장
- 생활복지국 김OO 국원
```

또 다른 예:

```text
Task: 협찬사 민감 계약안
공개 모드: RESTRICTED
열람:
- 회장
- 부회장
- 재무국장
- 사무국장
- 홍보국 김OO 국원
```

## 4.4 범용 ACL 모델

Task의 열람 범위를 별도 Join Table로 관리한다.

`task_access_rules`:

| 필드 | 설명 |
|---|---|
| `task_id` | 대상 Task |
| `subject_type` | `DEPARTMENT` / `USER` / `ROLE_GROUP` |
| `department_id` | 부서 대상일 때 사용 |
| `user_id` | 특정 개인 대상일 때 사용 |
| `role_group` | 1.6절의 `ALL_COUNCIL` / `DIRECTORS` / `EXECUTIVES` |
| `granted_by` | 권한을 부여한 사용자 |
| `created_at` | 생성 시각 |

Frontend의 체크박스가 아니라 **RLS SELECT 정책**이 공개 모드와 위 ACL을 함께 검사한다. Task의 Activity Log처럼 본문을 간접 노출할 수 있는 하위 데이터도 같은 Task 열람 함수를 사용한다. 댓글·첨부를 둘지는 부록 C.1의 D-5에서 정하며, 두게 되면 같은 함수를 사용한다.

## 4.5 ACL 수정 권한

- EXECUTIVE: 같은 Term의 모든 Task ACL 관리 가능
- DIRECTOR: `DEFAULT` 모드의 자기 국 Task 또는 자신이 `manager_id`인 `RESTRICTED` Task의 ACL 관리 가능
- MEMBER: ACL 변경 불가
- `manager_id` 변경: EXECUTIVE 또는 해당 Task의 현 관리 국장이 승인한 같은 Term의 DIRECTOR로 제한

ACL 변경은 Activity Log에 남긴다.

## 4.6 Task 변경 권한과 삭제 정책

Task의 열람 권한과 변경 권한은 별도로 판정한다.

| 행위 | MEMBER | DIRECTOR | EXECUTIVE |
|---|---|---|---|
| Task 생성 | X | 자기 국 또는 자신이 관리하는 Event | 같은 Term 전체 |
| 상태 변경 | 본인 담당 Task | 관리 가능한 Task | 같은 Term 전체 |
| 제목·담당자·마감일 변경 | X | 관리 가능한 Task | 같은 Term 전체 |
| 설명·첨부자료 변경 | 본인 담당 Task | 관리 가능한 Task | 같은 Term 전체 |
| ACL·공개 모드 변경 | X | 4.5절 범위 | 같은 Term 전체 |
| 보관 처리 | X | 관리 가능한 Task | 같은 Term 전체 |

MVP에서는 Task를 물리 삭제하지 않고 `archived_at`, `archived_by`를 기록해 목록에서 숨긴다. 재오픈, 담당자 변경, 공개 모드 변경, ACL 변경, 보관과 복원은 Activity Log에 남긴다. RLS의 UPDATE 정책은 행 접근만 확인하지 않고 변경 가능한 열과 상태 전이를 RPC 또는 Trigger에서 검증한다.

# 5. Event 및 행사 자료

## 5.1 Event 구성

```text
Event
├─ Overview
├─ Task
├─ Schedule
├─ Resources
├─ Meeting Minutes
└─ Handover
```

`events` 주요 필드:

- `term_id`
- `name`, `description`
- `status`: PLANNING / ACTIVE / COMPLETED / ARCHIVED
- `owner_department_id`
- `manager_id`
- `visibility_mode`: ALL_COUNCIL / RESTRICTED
- `starts_at`, `ends_at`
- `created_by`, `created_at`, `updated_at`

## 5.2 Event 열람 범위와 상속

`ALL_COUNCIL` Event는 같은 Term의 활성 학생회 구성원 전체가 열람한다. `RESTRICTED` Event는 회장단, 생성자, 관리자, 담당 국, `event_access_rules`에 지정된 부서·사용자·역할 그룹만 열람한다.

Event Overview, Resources, Schedule, Handover는 Event 열람 범위를 그대로 상속한다. Event 아래의 Task와 Meeting은 자체 ACL로 범위를 더 좁힐 수 있지만 Event 열람 범위를 넘어 공개할 수 없다. 유효 열람 권한은 다음 교집합으로 계산한다.

```text
하위 자원 유효 열람자 = Event 열람자 ∩ Task 또는 Meeting 열람자
```

Event를 `ALL_COUNCIL`에서 `RESTRICTED`로 바꾸거나 Event ACL에서 대상을 제거하면 하위 자료의 유효 접근도 즉시 좁아진다. 변경 화면은 영향을 받는 Task, Meeting, Resource 수를 보여 주고 Activity Log에 변경 전후 모드와 ACL을 남긴다.

### 범위 축소 시 충돌 처리

범위를 좁히면 1.7절 규칙을 어기는 지정(예: Event를 볼 수 없게 되는 Task 담당자나 회의록 편집자)이 생길 수 있다. 변경 화면은 이런 사용자·부서와 연결된 자원을 목록으로 보여 주고, 관리자는 다음 중 하나를 선택해야 저장할 수 있다.

1. 해당 사용자·부서를 Event ACL에 `USER`·`DEPARTMENT`로 남긴다.
2. 담당자·관리자·편집자를 다른 사용자로 바꾼다. 바꾸지 않은 미완료 Task 담당자는 비워 두고 재배정 필요로 표시한다.
3. 하위 ACL과 편집자 지정을 제거한다.

선택 결과는 하나의 트랜잭션으로 적용하고 Activity Log에 남긴다.

`event_access_rules`는 1.6절의 `DEPARTMENT / USER / ROLE_GROUP` 구조를 사용한다.

## 5.3 행사 자료

두 방식을 모두 지원한다.

| 유형 | 저장 방식 | 예시 |
|---|---|---|
| UPLOAD | Supabase Storage + metadata | PDF, XLSX, PNG |
| EXTERNAL_LINK | URL + 제목 + 설명 | Google Drive, OneDrive, 미리캔버스 |

`event_resources`에는 `resource_type`, `storage_path`, `external_url`, `title`, `description`, `uploaded_by` 등을 둔다.

업로드 자료는 기본적으로 **비공개 Storage Bucket**에 보관한다. `storage.objects`의 다운로드·업로드·삭제 권한은 해당 Event의 열람·관리 권한과 연결하고, 필요한 경우 짧은 만료 시간의 서명 URL을 발급한다. 저장 경로에는 `term_id/event_id`를 포함하고, 파일명만으로 권한을 판단하지 않는다.

외부 URL은 `https`만 허용하고 화면에서 새 창으로 연다. 외부 Drive URL은 이 플랫폼의 ACL만으로 보호할 수 없으므로 원본 서비스의 공유 권한을 등록·수정 시 확인한다.

업로드 파일은 1개당 10MB까지이고 PDF·PNG·JPG·WEBP·XLSX·DOCX·PPTX·HWP·HWPX만 받는다(0.2절). SVG·HTML처럼 브라우저에서 실행될 수 있는 형식과 ZIP·실행 파일은 받지 않고, 내려받을 때는 `attachment`로 응답해 브라우저에서 바로 열리지 않게 한다. 이 제한은 화면 안내만으로 두지 않고 Storage Bucket의 `file_size_limit`·`allowed_mime_types` 설정으로 강제한다. 10MB를 넘는 파일은 `EXTERNAL_LINK`로 등록하도록 안내한다. 총 사용량이 800MB(Free 1GB의 80%)를 넘으면 회장단에게 경고한다. 형식별 MIME 값과 악성 파일 검사 방식은 0.2절의 남은 운영값이다.

## 5.4 Schedule

`schedules`는 Term 공통 일정 또는 Event 일정으로 구분한다.

| 구분 | 열람 범위 |
|---|---|
| Term 공통 일정 | 같은 Term의 활성 학생회 구성원 전체 |
| Event 일정 | 해당 Event 열람 범위 상속 |

시간 일정은 `timestamptz`로 저장하고 화면은 `Asia/Seoul`로 표시한다. 종일 일정은 시간대 변환으로 날짜가 달라지지 않도록 별도 `start_date`, `end_date`를 사용한다. MVP에서는 반복 일정과 Google Calendar 양방향 동기화를 제외한다. Dashboard에는 사용자가 열람할 수 있는 일정만 노출한다.

## 5.5 Handover

Handover는 Event 또는 Department에 연결하며 다음 필드를 둔다.

- `term_id`, `event_id` 또는 `department_id`
- `title`, `content`
- `status`: DRAFT / PUBLISHED / ARCHIVED
- `owner_id`, `published_at`
- `created_at`, `updated_at`

초안은 작성자와 관리 권한자만 보고, 발행본은 해당 Event 열람자 또는 해당 Department의 활성 구성원과 회장단이 읽는다. 첨부 방식은 부록 C.1의 D-6에서 정하며, 업로드 첨부를 두게 되면 본문과 같은 권한을 사용한다. 이전 기수 자료를 새 운영진에게 전달할 때는 8절의 읽기 전용 Archive Grant를 사용한다. Handover 수정·발행·보관 이력은 Activity Log에 남긴다.

`event_id`와 `department_id` 중 정확히 하나만 채워지도록 CHECK 제약을 둔다. MVP의 Handover 본문은 BlockNote Block JSON으로 저장하며 실시간 공동 편집은 적용하지 않는다. 동시 수정은 `updated_at` 기반 낙관적 잠금으로 막는다.

## 5.6 Event 하위 자원 변경 권한

| 행위 | MEMBER | DIRECTOR | EXECUTIVE |
|---|---|---|---|
| Event 생성 | X | `owner_department_id`가 자기 국 | 같은 Term 전체 |
| Event 기본 정보·상태 변경 | X | 관리하는 Event | 같은 Term 전체 |
| Event 공개 모드·ACL 변경 | X | 관리하는 Event | 같은 Term 전체 |

| Resource 등록 | 열람 가능한 Event | 열람 가능한 Event | 같은 Term 전체 |
| Resource 수정·삭제 | 본인 등록 자료 | 관리하는 Event | 같은 Term 전체 |

## 6.1 Editor 사양 — 확정

회의록 Editor는 이번 버전에서 확정한다.

**BlockNote 기반 Notion형 Block Editor**를 사용한다.

지원 범위:

| 입력 | 동작 |
|---|---|
| `# 제목` | Heading 1 |
| `## 제목` | Heading 2 |
| `### 제목` | Heading 3 |
| `- 항목` | Bullet List |
| `1. 항목` | Numbered List |
| `- [ ] 할 일` | Todo |
| `> 내용` | Quote |
| `/콜아웃` | Callout |
| `/할일` | Todo |
| `/인용` | Quote |
| `/구분선` | Divider |
| `/코드` | Code Block |
| `/표` | Table |
| `/링크` | Link |

Slash Command는 한국어 alias를 둘 수 있다. 예: `/콜아웃`, `/강조`, `/callout` → 동일 기능.

### 구현 범위 구분

| 항목 | 구현 방식 |
|---|---|
| Heading, List, Todo(Check List), Quote, Code Block, Table, Divider | BlockNote 기본 Block 사용. 사용하는 BlockNote 버전에서 지원 여부를 Phase 0에 확인 |
| Callout | BlockNote 기본 Block이 아니므로 **커스텀 Block**으로 구현(아이콘·색상 type 속성) |
| Link | Block이 아니라 Inline Content. `/링크`는 URL 입력 후 현재 위치에 Link를 삽입하는 Slash 항목으로 구현 |
| 한국어 alias | Slash Menu 항목의 `aliases`에 한국어·영어 키워드를 함께 등록 |
| Markdown·JSON Export | BlockNote core 변환 기능 사용. 커스텀 Callout은 Markdown에서 Quote로 변환되는 손실을 허용 |

BlockNote의 일부 확장 패키지(예: XL 계열 Export·다단 Block)는 별도 라이선스 조건이 있으므로 MVP는 MPL-2.0 core 패키지 범위에서 구현하고, 확장 패키지 사용 시 라이선스를 먼저 검토한다.

원본 저장은 단순 Markdown 문자열이 아니라 Block 구조를 보존한다. CRDT가 적용된 상태에서는 Yjs 문서 상태를 원본으로 취급하고, 필요하면 Markdown/JSON으로 Export한다.

## 6.2 생성/작성 권한

| 행위 | 권한 |
|---|---|
| 회의록 생성 | 회장단(EXECUTIVE), 국장(DIRECTOR) |
| 제목/일시/Template 설정 | 생성자 또는 회장단 |
| 대표 작성자 지정 | 생성자 또는 회장단 |
| 지정 가능한 작성자 | 같은 Term 활성 구성원(Event 회의록은 Event 열람자만) |
| 본문 편집 | 같은 Term의 지정 편집자와 회장단 |
| 편집자 추가/제외 | 생성자 또는 회장단. 생성자인 국장은 자신이 만든 회의록만 관리 |
| 열람 범위 설정 | 생성자 또는 회장단 |
| Template 관리 | 회장단 |

작성자와 생성자는 별개다. `author_id`는 화면에 표시하는 대표 작성자이고, 실제 공동 편집 권한은 `meeting_editors`로 관리한다. 국장이 회의록을 만든 뒤 특정 국원을 대표 작성자와 편집자로 지정할 수 있으며, 여러 명의 편집자를 둘 수 있다. 대표 작성자는 자동으로 편집자에 포함된다. 편집자는 같은 Term의 활성 구성원이어야 한다.

편집자는 회의록 자체 열람 범위에 항상 포함된다(6.3절). Event에 속한 회의록이면 편집자는 1.7절에 따라 **Event를 열람할 수 있는 사용자 중에서만** 지정한다. 따라서 "편집 권한은 있으나 Event 교집합 때문에 열람할 수 없는" 상태는 생기지 않는다.

`CONFIRMED` 상태(6.8절)의 회의록은 편집자도 본문을 수정할 수 없다.

## 6.3 회의록 열람 범위

### 기본값

**국원 이상 학생회 구성원 전체**가 열람할 수 있다.

즉 일반 학생(`STUDENT`)은 기본 회의록을 볼 수 없다.

### 회의록 생성 시 선택

회의록 생성 화면에서 `열람 범위`를 반드시 확인/설정한다. 아래 4개 Preset 중 **하나만** 선택한다(조합하지 않음).

1. **전체** — 활성 학생회 구성원(MEMBER 이상) 전체
2. **특정 국** — 한 개 이상의 부서를 Multi-select
3. **국장단** — 모든 DIRECTOR + EXECUTIVE
4. **회장단** — EXECUTIVE (생성자·지정 편집자의 추가 접근은 아래 기본 규칙 적용)

`특정 국`은 단일 국으로 제한하지 않는다.

예:

```text
열람 범위: 특정 국
✓ 사무국
✓ 재무국
□ 홍보국
□ 생활복지국
```

또는

```text
열람 범위: 특정 국
□ 사무국
✓ 재무국
✓ 홍보국
✓ 생활복지국
```

처럼 임의의 복수 국을 선택할 수 있다.

### 범용 ACL 저장

UI에는 위 4개 Preset을 보여주되 DB는 범용 ACL로 저장한다.

`meeting_access_rules`:

| 필드 | 설명 |
|---|---|
| `meeting_id` | 회의록 ID |
| `subject_type` | `ROLE_GROUP` / `DEPARTMENT` / 향후 `USER` 확장 가능 |
| `role_group` | 1.6절의 `ALL_COUNCIL`, `DIRECTORS`, `EXECUTIVES` |
| `department_id` | 특정 국 Rule |
| `granted_by` | 설정자 |
| `created_at` | 생성 시각 |

열람 대상에는 선택한 Preset 외에 **해당 Term의 회장단·생성자·지정 편집자**가 항상 포함된다. 생성 화면은 이 추가 접근자를 명확히 보여 준다. 따라서 국장이 만든 `회장단` 범위의 회의록도 생성자 국장은 접근할 수 있다. `meeting_access_rules`는 Preset 대상만 저장하고, 기본 접근은 권한 함수에서 일관되게 계산한다. Event에 연결된 회의록은 5.2절에 따라 Event 열람 범위와 교집합을 적용한다.

이 구조라면 나중에 특정 개인만 추가 공개하는 기능을 넣더라도 스키마 변경이 거의 필요 없다. 단, `USER` 규칙을 실제 추가할 때는 `user_id` 필드·제약 조건·RLS 정책·UI를 함께 추가한다.

## 6.4 문자 단위 CRDT 공동 편집 — 확정

회의록은 단순 Live Sync가 아니라 **문자 단위 CRDT 공동 편집**까지 구현한다.

권장 구성:

```text
BlockNote Editor
      ↓ binding
Yjs Y.Doc / XmlFragment
      ↓ CRDT binary updates (클라이언트에서 묶음 병합)
Supabase RPC: save_meeting_update()   ← 편집 권한 검사 + 저장 + 순번 발급
      ↓ 같은 트랜잭션 안에서 realtime.send()
Supabase Realtime Private Broadcast
      ↓
다른 편집자의 Y.Doc에 Y.applyUpdate()
```

본문 Update 경로에는 Vercel 함수를 두지 않는다. 브라우저가 사용자 JWT로 Supabase RPC를 직접 호출하고, DB 함수가 권한 검사·저장·Broadcast 발행을 함께 처리한다. 키 입력마다 서버리스 함수를 호출하는 지연과 비용을 피하면서 "저장 확인 후 전파" 원칙을 유지한다.

Yjs는 동시 입력을 CRDT로 병합하므로 두 사용자가 같은 회의록을 동시에 수정해도 중앙 서버에서 문자 단위 충돌 해결 로직을 직접 작성할 필요가 없다.

### 역할 분리

| 구성 요소 | 역할 |
|---|---|
| BlockNote | Notion형 Block UI와 Markdown/Slash 입력 |
| Yjs | 문자/블록 단위 CRDT 상태 및 충돌 병합 |
| Supabase Realtime Broadcast | 저장된 Yjs Update 전달(DB 발행), Awareness 전달(클라이언트 발행) |
| Supabase Realtime Presence | 현재 문서 접속 사용자 목록 등 저빈도 상태 |
| PostgreSQL | 문서 Metadata, ACL, Update 저장·순번 발급·Broadcast 발행, Snapshot 영속화 |
| Vercel 서버 작업 | 회의록 생성 시 초기 Snapshot, 주기적 Snapshot 압축(Yjs를 Node에서 실행) |

**커서 위치·선택 영역처럼 빈번한 Awareness 정보는 Presence에 매 키 입력마다 넣지 않고 Broadcast/Yjs Awareness 계층으로 전달**한다. Presence는 접속자 목록처럼 저빈도 상태에 사용한다.

## 6.5 CRDT 영속화

Realtime Broadcast는 전송 계층이므로 문서 원본을 Broadcast에만 의존하지 않는다.

제안 테이블:

### `meeting_crdt_updates`

- `id`
- `meeting_id`
- `client_update_id` (재시도 중복 방지용 고유 ID, `meeting_id + client_update_id` 유일)
- `sequence_no` (회의록별 저장 순서, `meeting_id + sequence_no` 유일)
- `update_bytes` (`bytea`)
- `actor_id`
- `created_at`

`sequence_no`는 전역 identity 값을 쓰지 않는다. 동시 트랜잭션에서는 identity 발급 순서와 커밋 순서가 달라 "마지막으로 본 번호 이후" 조회가 늦게 커밋된 Update를 놓칠 수 있기 때문이다. 저장 함수는 `meeting_minutes.crdt_seq`를 `UPDATE … SET crdt_seq = crdt_seq + 1 RETURNING`으로 증가시켜 회의록 단위로 저장을 직렬화하고, 그 값을 `sequence_no`로 사용한다.

### `meeting_crdt_snapshots`

- `meeting_id`
- `state_bytes`
- `state_vector`
- `snapshot_version`
- `last_sequence_no` (해당 Snapshot에 포함된 마지막 Update)
- `created_at`

동작:

1. Client는 Yjs Update를 운영값(0.2절)으로 정한 짧은 간격 동안 모아 `Y.mergeUpdates()`로 하나로 합치고 `client_update_id`를 붙인다. 저장 확인 전에는 로컬 미전송 목록(IndexedDB 권장)에 유지한다. 한 번에 하나의 묶음만 전송 중으로 두고, 응답을 받은 뒤 다음 묶음을 보낸다.
2. `save_meeting_update()` DB 함수가 **현재 편집 권한**과 회의록 상태(`CONFIRMED` 여부)를 다시 검사하고, 순번을 발급해 Update를 저장한다. 같은 `client_update_id` 재요청은 중복 저장하지 않고 기존 순번을 반환한다.
3. 같은 함수가 저장 트랜잭션 안에서 `realtime.send()`로 `meeting:{meeting_id}` Private Channel에 `{sequence_no, update(base64)}`를 발행한다. 메시지는 커밋된 경우에만 전달된다. Broadcast가 유실돼도 수신 측은 `sequence_no` 공백을 발견하면 DB에서 빠진 구간을 다시 읽는다.
4. 저장 실패 시 Client가 지수 백오프로 재시도하고, 저장 확인 전에는 UI에 `저장 완료`로 표시하지 않는다. 권한 거부 응답이면 재시도하지 않고 편집기를 읽기 전용으로 바꾼 뒤 미저장 내용이 있음을 알린다.
5. 신규 접속·재접속 사용자는 최신 Snapshot + `last_sequence_no` 이후 Update를 가져오고, Yjs 상태 벡터로 누락 차이를 재동기화한다. 이후 받은 Broadcast 중 이미 적용한 순번은 무시한다(Yjs 적용 자체도 멱등).
6. Snapshot 생성·오래된 Update 정리는 회의록 행 잠금으로 동시 저장과 충돌하지 않게 한다. `Y.mergeUpdates()`만으로 삭제된 내용이 완전히 정리되지는 않으므로 운영값 주기마다 신뢰된 서버 작업이 Y.Doc을 로드해 전체 Snapshot을 만든다. 정리하는 Update는 새 Snapshot의 `last_sequence_no` 이하만 대상으로 한다.

Realtime Broadcast 수신이나 클라이언트 로컬 상태만으로 영속 저장을 보장했다고 간주하지 않는다. 저장 실패·연결 끊김·중복 전송·Broadcast 유실·동시 Snapshot을 완료 기준에서 테스트한다.

Phase 0에서 확인할 기술 항목:

- 사용하는 Supabase 버전에서 `realtime.send()`의 Private Channel 발행과 페이로드 크기 한도
- 큰 붙여넣기처럼 한도를 넘는 Update는 Broadcast 대신 "새 Update 있음" 신호만 보내고 수신 측이 DB에서 읽게 하는 처리
- 묶음 간격별 체감 지연과 Realtime 메시지 사용량

## 6.6 Realtime 채널 보안

회의록 채널은 `meeting:{meeting_id}` 형태의 **Private Channel**로 운영한다.

채널 수신 권한은 회의록 열람 함수를 검사한다. CRDT Update는 DB 함수만 발행하므로, 클라이언트의 Broadcast 송신은 Awareness 이벤트에 한해 편집 함수를 통과한 사용자에게만 허용하고 `crdt-update` 이벤트 이름의 클라이언트 송신은 거부한다. DB의 Snapshot/Update SELECT는 읽기 권한을 검사하고, Update INSERT는 테이블에 직접 허용하지 않고 `save_meeting_update()` 함수로만 수행한다. Snapshot 생성·교체·정리는 신뢰된 서버 작업만 수행한다. Presence 수신/게시 및 Awareness Broadcast도 별도 권한을 둔다. 채널은 `private: true`로 생성하고, Realtime의 공개 채널 허용 설정을 비활성화한다.

즉 회의록 본문 SELECT 권한이 없는 사용자는:

- DB에서 회의록을 읽을 수 없고
- 해당 Realtime Broadcast를 받을 수 없고
- Presence 상태도 받을 수 없어야 한다.

이로써 화면 URL을 직접 입력하거나 Realtime 채널 이름을 알아내도 신규 접근을 막는다. 다만 Supabase Realtime은 접속 중 권한 판정을 캐시하므로 ACL을 회수해도 기존 연결의 수신 권한이 즉시 사라진다고 가정하지 않는다. 짧은 JWT 유효 기간과 권한 변경 시 클라이언트 재구독 신호를 함께 적용하고, 권한 회수 후 최대 수신 가능 시간을 운영 정책으로 정해 테스트한다. 저장 API는 연결 상태와 무관하게 매 요청에서 최신 권한을 검사한다.

## 6.7 Meeting Template

회장단이 회의록 기본 Template을 생성·수정·비활성화한다.

예:

- 전체회의
- 국장단 회의
- 국별회의
- 행사 TF 회의

Template은 BlockNote 초기 Block 구조로 저장한다. Template은 Term에 속하며 새 Term으로 자동 복제하지 않는다(8절).

### Template 적용 시점

Template을 각 클라이언트가 처음 열 때 Y.Doc에 넣으면, 두 사용자가 새 회의록을 동시에 열었을 때 같은 Template이 두 번 삽입된다. 이를 막기 위해 회의록 생성 요청을 처리하는 신뢰된 서버 작업이 Template Block으로 Y.Doc을 만들고 **`snapshot_version = 1`인 초기 Snapshot을 회의록 행과 같은 트랜잭션에서 저장**한다. 클라이언트는 항상 Snapshot에서 시작하며 Template을 직접 삽입하지 않는다.

## 6.8 회의록 상태

`meeting_minutes.status`는 `DRAFT / CONFIRMED / ARCHIVED`로 관리한다.

| 상태 | 본문 편집 | 전환 권한 |
|---|---|---|
| `DRAFT` | 편집자·회장단 | 생성 시 기본값 |
| `CONFIRMED` | 불가(읽기 전용) | 생성자 또는 회장단이 확정. 확정 시 최종 Snapshot을 만든다 |
| `ARCHIVED` | 불가, 목록에서 숨김 | 생성자 또는 회장단 |

`CONFIRMED`를 `DRAFT`로 되돌리는 것은 회장단만 가능하며 사유와 함께 Activity Log에 남긴다. 상태 전환 시 Realtime 채널에 재구독 신호를 보내 편집기를 읽기 전용으로 바꾼다.

# 7. Suggestion

일반 학생은 건의사항을 작성하고 본인 건의의 처리 상태를 볼 수 있다.

`suggestions` 주요 필드:

- `term_id`
- `title`, `content`
- `status`: RECEIVED / IN_REVIEW / RESOLVED / CLOSED
- `assigned_department_id`, `assigned_user_id`
- `created_at`, `updated_at`, `resolved_at`

작성자는 자신의 건의 내용·상태·작성자에게 공개된 답변을 볼 수 있다. 학생회 처리 담당자는 배정된 건의 내용과 내부 메모를 볼 수 있지만 작성자 신원은 볼 수 없다. 회장단은 같은 Term의 전체 건의와 신원 정보를 확인하고 담당자를 지정할 수 있다.

## 7.1 작성자 신원

건의사항 작성자의 이름/이메일은 다음 사용자만 확인할 수 있다.

- 작성자 본인
- 건의가 속한 Term의 활성 EXECUTIVE(회장·부회장)

Position 이름이 아니라 Role로 판정한다. 회장·부회장 외 다른 사람에게 EXECUTIVE를 부여하면 그 사람도 신원을 볼 수 있으므로, EXECUTIVE 부여 화면에 이 사실을 경고로 표시한다.

국장과 국원에게 건의 처리를 맡기더라도 작성자의 신원 정보는 전달하지 않는다.

UI에서 이름을 가리는 수준이 아니라 DB 구조에서 작성자 신원을 분리한다. `suggestions`에는 내용·상태·처리 정보만 두고, `suggestion_authors(suggestion_id, author_user_id)`는 작성자 본인과 해당 Term의 EXECUTIVE만 SELECT할 수 있게 한다. 처리 담당 국장·국원은 `suggestions`만 조회한다. 기본 테이블의 불필요한 SELECT 권한을 철회하고, 공개 View를 사용한다면 `security_invoker` 등으로 RLS 우회를 막는다. Activity Log·알림·검색 결과·Realtime payload에도 신원이 섞이지 않는지 확인한다.

## 7.2 답변과 내부 메모

건의 처리 기록은 `suggestion_messages`로 분리한다.

| 유형 | 열람자 |
|---|---|
| `AUTHOR_VISIBLE` | 작성자, 배정된 처리자, 회장단 |
| `INTERNAL` | 배정된 처리자와 회장단 |

"배정된 처리자"는 `assigned_user_id`에 지정된 사용자다. 부서만 배정된 경우의 처리자는 부록 C.1의 D-11에서 정한다.

작성자에게 보이는 답변과 내부 협의 메모를 같은 필드에 섞지 않는다. 메시지를 작성하거나 유형을 바꾸는 행위, 담당자와 상태를 바꾸는 행위는 Activity Log에 남긴다. Activity Log에는 작성자 ID나 건의 본문을 복사하지 않는다.

건의 작성 API는 로그인한 학교 계정만 호출할 수 있고 서버에서 작성자 연결을 만든다. 클라이언트가 다른 사용자의 ID를 `author_user_id`로 전달할 수 없게 한다. 제출 중복을 막기 위해 요청별 고유 ID를 받고, 운영값으로 정한 빈도 제한을 적용한다.

`suggestions`에는 작성자 열이 없으므로, 작성자 본인의 조회는 `suggestion_authors`를 확인하는 `SECURITY DEFINER` 함수(고정 `search_path`)로 판정한다. 이 함수는 참/거짓만 반환하고 작성자 ID를 돌려주지 않는다.

## 7.3 Term 전환과 건의

새 건의는 작성 시점의 ACTIVE Term에 속한다. 미처리 건의는 **마감** 정책(0.2절)으로 처리하며 새 Term으로 이월하지 않는다.

- 이전 회장단은 Term 종료 전에 `RECEIVED`·`IN_REVIEW` 건의에 작성자 공개 답변을 남기고 `CLOSED`로 처리한다.
- Term 전환 화면은 남은 미처리 건의 수와 목록을 보여 준다. 전환 시점까지 처리하지 않은 건의는 전환 트랜잭션에서 기본 안내 답변과 함께 `CLOSED`로 바뀐다. 안내 문구는 0.2절 건의 처리 시간 항목과 함께 정한다.
- 새 회장단은 이전 Term 건의의 작성자 신원을 볼 수 없다. Archive Grant에서도 작성자 정보는 제외한다(8.1절).
- 마감 답변에는 필요하면 새 기수에 다시 제출해 달라는 안내를 넣는다. 작성자가 같은 내용을 다시 제출하면 새 Term의 새 건의로 처리한다.

작성자는 Term과 무관하게 자신이 작성한 모든 건의와 공개 답변을 계속 볼 수 있다.

# 8. Term과 다음 기수 정책

`Term`은 계속 사용한다.

예:

- 2026 제N대 학생회
- 2027 제N+1대 학생회

하지만 다음 기수 생성 시 다음 기능은 **개발하지 않는다**.

- 이전 부서 자동 복제
- 구성원 자동 복제
- Event/Task 자동 복제
- Template 자동 복제
- ACL 자동 복제

새 Term은 빈 상태로 생성한다. 데이터 복제 정책은 추후 별도 의사결정 후 개발한다. 모든 Membership·부서·ACL 대상은 리소스의 `term_id`와 같은 Term인지 검증한다. 다른 Term에서 회장단이었던 사용자가 현재 Term 자료에 자동 접근하지 않는다. 새 Term의 첫 EXECUTIVE 초기화 절차는 2.2절을 따른다.

## 8.1 Term 상태와 보관 자료

Term 상태는 `DRAFT / ACTIVE / CLOSED`로 관리하며 한 시점에 하나의 Term만 ACTIVE로 둔다(부분 유일 제약). CLOSED Term은 기본적으로 읽기 전용이다. 과거 기록을 수정해야 할 때는 현재 ACTIVE Term의 회장단이 사유를 입력해 제한된 관리 절차로 처리하고 Activity Log에 남긴다.

### Term별 접근 규칙

| Term 상태 | 해당 Term Membership 보유자 | 다른 사용자 |
|---|---|---|
| `DRAFT` | EXECUTIVE만 조직·승인 계정·Template 준비 가능. 다른 구성원은 아직 접근하지 않음 | 접근 불가 |
| `ACTIVE` | 1–7절 권한 그대로 적용 | 접근 불가 |
| `CLOSED` | 접근 불가. Term 종료 시 모든 Membership에 `left_at`을 기록하고 비활성화 | 유효한 Archive Grant 범위만 읽기 |

이전 기수 구성원이 새 Term에도 소속되면 새 Term Membership으로만 권한을 얻는다. 이전 Term 자료가 필요하면 다른 사용자와 같이 Archive Grant를 받는다.

`departments`, `positions`, `meeting_templates`는 Term에 속한다. 새 Term은 이 값들을 빈 상태로 시작하며, 회장단이 관리 화면에서 새로 만든다. `dashboard_links`만 전역 설정이다(3.2절).

### Term 전환 절차

1. 운영자가 새 Term을 `DRAFT`로 만들고 첫 EXECUTIVE를 2.2절 절차로 등록한다.
2. 새 회장단이 부서·직책·승인 계정을 준비한다.
3. 전환 시점에 단일 트랜잭션으로 이전 Term을 `CLOSED`, 새 Term을 `ACTIVE`로 바꾸고 이전 Term Membership을 종료한다. 미처리 건의는 7.3절에 따라 마감한다.
4. 열린 Realtime 연결에 재구독 신호를 보낸다.
5. 공용 계정(GitHub Organization·Supabase·Vercel·Google Cloud 등) 비밀번호와 관리 권한을 새 회장·부회장에게 넘기고 비밀번호를 바꾼다. 비밀번호는 이 플랫폼, 저장소, 채팅방에 기록하지 않는다.

새 운영진이 이전 자료를 인수인계받을 수 있도록 `term_archive_access`를 둔다.

| 필드 | 설명 |
|---|---|
| `source_term_id` | 읽을 과거 Term |
| `grantee_user_id` | 현재 활성 Membership을 가진 사용자 |
| `scope_type` | TERM / EVENT / DEPARTMENT / HANDOVER |
| `scope_id` | 범위에 해당하는 자원 ID(`TERM`이면 비움) |
| `expires_at` | 열람 만료 시각 |
| `granted_by` | 권한을 부여한 회장단 |
| `revoked_at`, `revoked_by` | 회수 시각과 회수자 |

Archive Grant는 읽기만 허용하고 자동 생성하지 않는다. 현재 회장단이 필요한 범위와 기간을 지정하며 만료·회수 이력을 남긴다(`revoked_at`, `revoked_by`). Suggestion 작성자 정보와 제한 공개 Task·Meeting은 별도 명시가 없으면 Archive Grant 대상에서 제외한다.

Grant는 조회 시점마다 다음을 모두 만족할 때만 유효하다: `expires_at`이 지나지 않음, 회수되지 않음, `grantee_user_id`가 현재 ACTIVE Term의 활성 Membership을 가짐. `scope_id`는 여러 테이블을 가리키므로 FK 대신 저장 시 `scope_type`별로 대상이 `source_term_id`에 속하는지 검증하는 함수를 둔다. `scope_type = TERM`은 해당 Term의 비제한 자료 전체를 뜻하므로 부여 화면에서 별도 확인을 받는다.

## 9.2 권한 계산의 기반 테이블

RLS 함수가 매 요청 참조하는 테이블이므로 필드와 제약을 먼저 확정한다. 전체 필드는 부록 B에 둔다.

| Table | 핵심 필드 | 제약 |
|---|---|---|
| `terms` | `name`, `status`(DRAFT/ACTIVE/CLOSED), `starts_on`, `ends_on` | `status = ACTIVE` 행은 하나만(부분 유일 Index) |
| `profiles` | `id`(= `auth.users.id`), `email`, `display_name`, `student_no`(선택) | `email`은 소문자 정규화. 사용자가 직접 수정할 수 있는 열은 `display_name`뿐 |
| `departments` | `term_id`, `name`, `sort_order`, `is_active` | `term_id + name` 유일 |
| `positions` | `term_id`, `name`, `sort_order`, `is_active` | `term_id + name` 유일. 권한 판정에 사용하지 않음 |
| `memberships` | `term_id`, `user_id`, `role`, `department_id`, `position_id`, `is_active`, `joined_at`, `left_at`, `approved_account_id` | 활성 행 기준 `term_id + user_id` 유일. `role ≠ EXECUTIVE`이면 `department_id` 필수. 부서·직책은 같은 Term이어야 함 |
| `approved_council_accounts` | 2.2절 필드 | `term_id + lower(email)` 유일 |

`memberships`, `approved_council_accounts`, `terms`에는 클라이언트의 직접 INSERT/UPDATE/DELETE를 허용하지 않고 권한 검사를 포함한 RPC로만 변경한다.

# 10. RLS 및 Permission 설계

## 10.1 핵심 원칙

1. 일반 학생은 학생회 내부 데이터에 접근하지 않는다.
2. 현재 Term 내부 접근은 같은 Term의 활성 `memberships`가 있는 계정만 허용한다. CLOSED Term은 유효한 `term_archive_access`로만 읽는다(8.1절).
3. Event 하위 자료의 SELECT는 Event 열람 범위를 먼저 검사한다.
4. Task SELECT는 Event 범위 안에서 공개 모드·해당 Term의 기본 접근자·`task_access_rules`를 함께 검사한다.
5. Meeting SELECT/Realtime 수신은 Event 범위와 회의록 열람 함수를 검사한다. CRDT Update 저장은 `save_meeting_update()` 함수만 수행하며 편집 함수와 회의록 상태를 검사한다.
6. 회의록 ACL 변경은 생성자 DIRECTOR 또는 해당 Term의 EXECUTIVE만 가능하다.
7. 건의 작성자 신원은 작성자 본인과 해당 Term의 EXECUTIVE만 확인한다.
8. Secret/Service Role Key는 Browser에 노출하지 않는다.
9. Task/Meeting 하위 데이터, Storage 객체, Activity Log도 상위 리소스의 열람 경계를 따른다. 이후 검색·알림 기능을 추가할 때도 같은 열람 함수를 사용한다(MVP 제외, 13.2절).
10. 권한 판단에 사용하는 Membership은 리소스와 같은 Term의 활성 행이어야 한다.
11. 담당자·편집자·ACL 대상 지정은 상위 Event 열람 범위 안에서만 허용한다(1.7절).
12. RLS와 Realtime 정책은 기능 개발 단계마다 허용/거부 사례로 검증한다.

## 10.3 Activity Log

`activity_logs`는 감사 기록이므로 일반 사용자가 UPDATE 또는 DELETE할 수 없는 append-only 구조로 둔다.

주요 필드:

- `term_id`
- `resource_type`, `resource_id`
- `action`
- `actor_id`
- `before_summary`, `after_summary`
- `request_id`
- `created_at`

Actor와 시각은 서버에서 기록하고 클라이언트 입력을 신뢰하지 않는다. 본문 전문, 건의 작성자 ID, CRDT 바이너리, 파일 서명 URL, OAuth Token은 로그에 넣지 않는다. 건의 작성 행위 자체는 `actor_id` 없이 기록한다. 로그 조회 권한은 대상 자원의 열람 권한을 넘지 않으며, 보안 감사용 전체 조회는 EXECUTIVE로 제한한다. CRDT Update 저장은 Activity Log에 행 단위로 남기지 않는다(`meeting_crdt_updates.actor_id`로 충분).

## 10.4 RLS 구현 규칙

권한 함수는 모든 행 접근에서 호출되므로 다음 규칙으로 작성한다.

- 권한 함수는 `private` 같은 비공개 스키마에 두고 `SECURITY DEFINER`, `STABLE`, 고정 `search_path`로 선언한다. `public` 스키마에 두지 않아 API로 직접 호출되지 않게 한다.
- 정책에서는 `auth.uid()`와 사용자 단위 함수 호출을 `(select auth.uid())`, `(select private.current_membership(term_id))`처럼 감싸 행마다 재평가되지 않게 한다.
- 열람 함수 하나(`can_read_task`, `can_read_meeting`, `can_read_event` 등)를 SELECT 정책·하위 테이블 정책·Storage 정책·Realtime 정책이 공유한다.
- `memberships(term_id, user_id) where is_active`, 각 ACL 테이블의 `(자원 ID, subject_type)`, `meeting_editors(meeting_id, user_id)`, `meeting_crdt_updates(meeting_id, sequence_no)`에 Index를 둔다.
- 허용·거부 사례는 `pgTAP` 또는 동등한 DB 테스트로 작성해 CI에서 실행한다. 사례에는 다른 Term 사용자, 종료된 Membership, RESTRICTED Event 밖 사용자, 회수 직후 사용자를 포함한다.

## 11.2 실행 환경과 요금제

| 환경 | 앱 | DB | 용도 |
|---|---|---|---|
| 로컬 | `npm run dev` | 로컬 Supabase(Docker) | 개발·연습. `db reset`은 로컬에서만 허용 |
| Preview | Vercel Preview(PR별 주소) | Supabase `dev` 프로젝트 | PR 확인 |
| Production | Vercel Production | Supabase `prod` 프로젝트 | 실제 운영 |

요금제는 Supabase Free와 Vercel Hobby로 확정했다(0.2절). Supabase Free의 주요 한도는 DB 500MB, Storage 1GB, 다운로드 트래픽 월 5GB, 월간 활성 사용자 50,000명이다. 무료 프로젝트는 2개뿐이라 dev·prod에 모두 사용했고, 1주일 동안 요청이 없으면 일시 중지된다. 시험 기간처럼 사용이 끊기는 시기를 대비해 GitHub Actions keep-alive 작업으로 dev·prod에 주기적으로 요청을 보낸다. 규모가 커지면 Supabase Pro(월 $25부터)를 검토한다.

Free 요금제에서 확인할 것:

- **백업:** Free 요금제가 제공하는 백업 범위를 확인한다. 부족하면 정기 `pg_dump`와 Storage 사본을 만드는 자체 백업 방식과 담당자를 정한다(12.1절).
- **Realtime:** 동시 접속·메시지 한도를 공동편집 기술 검증 때 실제 묶음 간격으로 측정한다.

# 14. 완료 기준

1. 회장단이 학생회 계정을 일괄 등록하고 Role/부서/직책을 사전에 설정할 수 있다.
2. 국장은 자기 국 MEMBER를 추가·제외할 수 있다.
3. 회의록 기본 열람 범위는 국원 이상 전체이며 생성 시 전체/복수 국/국장단/회장단 중 선택할 수 있다.
4. `특정 국`은 A+B처럼 2개뿐 아니라 B+C+D처럼 임의 개수의 부서를 선택할 수 있다.
5. 회의록 DB 조회 권한과 Realtime Channel 가입 권한이 동일 ACL을 사용한다.
6. BlockNote Editor의 Markdown/Slash Command 사양은 확정 상태로 구현된다.
7. Yjs를 이용해 문자 단위 CRDT 공동 편집이 가능하다.
8. Task는 기본 공개/제한 공개 모드를 선택하고, 권한자가 특정 부서 또는 학생회 구성원 N명을 열람자로 지정할 수 있다. 제한 공개 Task는 담당 국 전체에 자동 공개되지 않는다.
9. 국원은 권한이 부여되지 않은 타부서 Task와 그 하위 자료를 조회하지 못한다.
10. 건의 작성자 신원은 작성자 본인과 회장단만 볼 수 있다.
11. Event 자료는 Supabase 업로드와 외부 Drive URL을 모두 지원한다.
12. 완료 Task도 수정/재오픈할 수 있고 변경 이력이 남는다.
13. 다음 기수 데이터 자동 복제 기능은 구현하지 않는다.
14. 운영 요소는 가능한 한 관리자 UI + DB 기반으로 관리하며 부서명/링크/회의 범위를 코드에 박지 않는다.
15. 회의록 열람자와 편집자를 구분하고, 열람자에게 CRDT 저장·Broadcast 송신 권한을 주지 않는다.
16. CRDT 저장 실패 후 재시도, 중복 Update, 재접속, 동시 편집·Snapshot 상황에서 데이터가 유실되지 않는다.
17. 권한을 회수한 사용자는 DB에 즉시 쓰거나 읽지 못하며, Realtime 수신 지연은 정한 최대 허용 시간 안에 종료된다.
18. 건의 처리 담당자는 API·로그·검색·알림에서 작성자 신원을 볼 수 없다.
19. 업로드 자료는 비공개 Storage 정책과 파일당 10MB·허용 형식 제한을 따르고(Bucket 설정으로 강제), 외부 링크는 원본 서비스의 공유 권한을 확인한다.
20. 새 Term의 첫 회장단 초기화와 기존/다른 Term 계정의 접근 차단을 검증한다.
21. Event의 열람 범위가 Resource·Schedule·Handover에 상속되고, Task·Meeting ACL이 Event 범위를 넘어 공개되지 않는다.
22. Role별 Permission은 고정 매핑으로 계산하며 Position 이름이나 화면 표시만으로 권한을 부여하지 않는다.
23. Task 변경 가능 필드와 상태 전이를 서버에서 검사하고, 삭제 대신 보관·복원 이력을 남긴다.
24. 건의 작성자 공개 답변과 내부 메모가 분리되고, 작성자는 내부 메모를 조회하지 못한다.
25. CLOSED Term은 읽기 전용이며, 새 운영진은 만료 시간이 있는 Archive Grant 범위에서만 이전 자료를 읽는다.
26. Activity Log는 일반 사용자가 수정·삭제할 수 없고 민감한 본문·신원·Token·서명 URL을 저장하지 않는다.
27. 시간 일정과 종일 일정의 저장 방식을 구분하고 `Asia/Seoul` 표시를 검증한다.
28. 운영값의 `TBD`와 부록 C.1의 "제안" 상태가 해소되고 DB·Storage 복구 절차를 한 번 이상 점검한 뒤 배포한다.
29. 학교 외 Google 계정과 이메일 미검증 계정은 Auth Hook에서 거부되어 `auth.users`·`profiles`에 행이 생기지 않는다.
30. RESTRICTED Event에서 Event를 열람할 수 없는 사용자는 Task 담당자·관리자, 회의록 작성자·편집자, ACL 대상으로 지정되지 않는다(UI와 RPC 모두).
31. Event 범위를 좁힐 때 충돌하는 지정이 목록으로 표시되고, 해결 방법을 선택해야 저장된다.
32. CRDT Update는 `save_meeting_update()`로만 저장되며, 저장이 커밋된 Update만 Broadcast된다. 클라이언트가 직접 `crdt-update`를 송신하면 거부된다.
33. 동시 저장에서 `sequence_no`가 회의록별로 공백·중복 없이 발급되고, Broadcast를 놓친 클라이언트가 공백을 감지해 DB에서 복구한다.
34. 두 사용자가 새 회의록을 동시에 열어도 Template 내용이 한 번만 나타난다.
35. `CONFIRMED` 회의록은 편집자도 저장할 수 없다.
36. Term 전환 후 이전 Term 구성원은 Archive Grant 없이 이전 Term 자료를 읽지 못하고, 미처리 건의는 마감 정책대로 이전 Term에서 닫히며 새 회장단에 작성자 신원이 노출되지 않는다.
37. Membership 종료 시 관리 책임이 지정된 사람 또는 국장·회장단으로 넘어가고, 담당자가 비활성인 Task가 표시된다.
38. 허용·거부 RLS 사례가 DB 테스트로 자동 실행된다.
39. 개인정보처리방침을 게시하고, Google OAuth 동의 화면 게시에 필요한 항목(앱 이름, 지원 이메일, 개인정보처리방침 링크, 승인된 도메인)을 준비한다.

# 부록 A 실시간 공동편집 기술 근거

- BlockNote 공식 문서는 Real-time Collaboration 기능이 Yjs를 사용하며 Yjs Provider를 통해 Update를 전송하는 구조를 제공한다.  
  [BlockNote Collaboration 문서](https://www.blocknotejs.org/docs/features/collaboration)
- Yjs는 동시 수정이 자동으로 병합되는 CRDT이며 문서 Update는 순서와 중복 적용에 안전하도록 설계되어 있다.  
  [Yjs 문서](https://docs.yjs.dev/)  
  [Yjs Document Updates 문서](https://docs.yjs.dev/api/document-updates)
- Supabase Realtime Broadcast는 WebSocket 기반 low-latency 메시지 전달을 제공하고, Private Channel에 RLS 기반 Authorization을 적용할 수 있다. Broadcast 수신/송신 권한은 분리되며, 접속 중 권한은 캐시된다.  
  [Supabase Broadcast 문서](https://supabase.com/docs/guides/realtime/broadcast)  
  [Supabase Realtime Authorization 문서](https://supabase.com/docs/guides/realtime/authorization)
- Supabase Presence는 접속 상태 공유에 적합하지만 공식 문서상 고빈도 상태 전송에는 적합하지 않으므로 커서/selection 같은 빈번한 Awareness는 Broadcast/Yjs 계층으로 처리하는 것이 적절하다.  
  [Supabase Presence 문서](https://supabase.com/docs/guides/realtime/presence)
- Google 계정의 이메일 도메인만으로 Workspace 소속을 식별할 수 없으며, Workspace 제한이 필요하면 `hd` 클레임을 확인한다.  
  [Google OpenID Connect 문서](https://developers.google.com/identity/openid-connect/reference)
- Supabase RLS는 행 단위이며, 민감한 열은 별도 테이블·권한 설계가 필요하다. Storage 객체에도 RLS 정책을 적용할 수 있다.  
  [Supabase Column Level Security 문서](https://supabase.com/docs/guides/database/postgres/column-level-security)  
  [Supabase Storage Access Control 문서](https://supabase.com/docs/guides/storage/security/access-control)

# 부록 C 기능별 화면 명세

본문은 권한·데이터 규칙을 정한다. 이 부록은 사용자가 보는 화면, 흐름, 입력값처럼 본문에 없던 부분을 채운다.

- **C.1**은 DB 구조나 RLS에 영향을 주는 미정 항목이다. 리드가 해당 기능의 기반 작업(Migration·RLS·함수)을 시작하기 전에 확정한다.
- **C.2**는 모든 화면에 공통으로 적용하는 규칙이다.
- **C.3**은 기능별 화면의 틀이다. 위젯 개수, 정렬, 문구처럼 화면 안에서만 정해지는 값은 각 주차 Issue의 "확인 기준"에서 확정한다. 여기 적힌 값은 기본 제안이다.

## C.1 기반 작업 전 확정할 항목

| D-14 | Profile 수집 항목 | **학번(`student_no`)을 받는다.** `display_name`의 처음 값은 Google 이름이며(이미 구현) 본인이 고칠 수 있다. 입력 시점(일괄 등록 때 함께 / 본인 입력)·형식 검증·열람 범위는 구성원 기반(3주차 기반) 전에 정한다. 학번은 같은 기수 구성원 전체에게 보이지 않게 열람 범위를 좁히고, 개인정보처리방침에 수집 항목으로 적는다 | 리드 결정(10/29). 지금 RLS는 같은 기수 구성원이 Profile 전체 열을 볼 수 있으므로 학번 수집 전에 열람 제한이 필요하다 | 2.1, 9.2 | 11/5 | **확정** |
| D-15 | Event 상태 전환 | 관리 권한자가 `PLANNING`→`ACTIVE`→`COMPLETED`→`ARCHIVED` 순서로 직접 바꾼다. `COMPLETED`는 목록에서 "지난 행사"로 옮겨지되 수정할 수 있다. `ARCHIVED`는 읽기 전용이며 되돌리기는 회장단만 한다 | 날짜로 자동 전환하면 연기된 행사를 다루기 어렵다 | 5.1, 5.6 | 11/19 | 제안 |

## C.2 공통 화면 규칙

### 화면 주소 (제안)

### 화면 상태

모든 데이터 화면은 네 상태를 보여 준다.

| 상태 | 표시 |
|---|---|
| 로딩 | 실제 레이아웃 모양의 자리 표시(Skeleton). 문구만 있는 "로딩 중"은 쓰지 않는다 |
| 빈 목록 | "아직 ○○가 없습니다." 만들 권한이 있는 사용자에게만 만들기 버튼을 보여 준다 |
| 오류 | "불러오지 못했습니다." + 다시 시도 버튼. 기술 오류 내용은 화면에 보이지 않고 로그에 남긴다(12.1절) |
| 권한 없음·없는 자원 | 둘을 구분하지 않고 "찾을 수 없거나 볼 권한이 없습니다"로 보여 준다. 존재 여부를 노출하지 않기 위해서다. RLS가 빈 결과를 돌려주는 경우도 같다 |

### 목록

- 한 페이지 20개, 페이지네이션 사용(12.1절).
- 제목 필터만 둔다. 통합 검색은 MVP에서 제외한다(13.2절).
- 기본 정렬은 C.3의 화면별 값을 따른다.

### 입력과 저장

- 제목은 1~100자. 필수 항목에 표시를 붙인다. 길이·형식 제한은 화면과 DB CHECK 제약에 함께 둔다.
- 날짜·시간은 `Asia/Seoul`로 보여 주고 입력받는다(5.4절).
- 저장 중에는 버튼을 비활성화해 중복 제출을 막는다. 성공하면 짧은 알림을 보여 주고, 실패하면 입력한 내용을 그대로 둔다.
- 되돌릴 수 없는 작업(Membership 종료, 회의록 확정, 발행, 기수 전환, 작성자 공개 답변 등록)은 확인 대화상자를 거친다.

### 공통 표시

- 비활성 구성원은 이름 옆에 "(비활성)"을 붙인다(1.5절).
- 375px 폭에서 깨지지 않는다. 관리 화면은 데스크톱 우선이지만 모바일에서도 읽을 수 있어야 한다(12.1절).
- 키보드로 주요 흐름을 끝낼 수 있고 focus 표시가 보인다(12.1절).
