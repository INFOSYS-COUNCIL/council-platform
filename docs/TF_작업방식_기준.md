## 1. 작업 방식 한눈에 보기

### 1.1 원칙

| 원칙 | 뜻 |
|---|---|
| **기다리지 않는다** | 한 사람이 끝나야 다음 사람이 시작하는 구조를 만들지 않는다. 처음부터 동시에 일할 수 있게 나눈다. |
| **판을 먼저 깐다** | 리드가 DB 구조·권한·함수 이름·화면 경로를 먼저 정한다(기반 작업). 팀원은 그 위에서 각자 화면을 완성한다(기능 작업). |
| **파일을 나눠 갖는다** | Issue마다 고칠 수 있는 파일이 정해져 있다. 같은 파일을 두 사람이 고치지 않는다. |
| **작게 자주 합친다** | Issue 하나 = 브랜치 하나 = PR 하나. 일주일 안에 끝나는 크기로 자른다. |
| **이해한 것만 합친다** | AI가 만든 코드라도, 작성자가 "무엇을 왜 바꿨는지" 설명할 수 있어야 Merge한다. |
| **보안은 DB가 막는다** | 화면에서 버튼을 숨기는 것은 편의일 뿐이다. 실제 권한은 Supabase RLS가 판단한다. |

### 1.2 역할

| 사람 | 역할 | 주로 하는 일 |
|---|---|---|
| 한지석 | 리드 | **기반 작업**, Issue 작성·배정, 최종 리뷰·Merge, 공용 파일 관리 |
| 강주원 · 정재헌 | 화면 담당 | **기능 작업** 중 입력 폼·화면 구성이 많은 Issue |
| 이은규 · 조수빈 | 연결·검증 담당 | **기능 작업** 중 데이터 처리·권한 확인·테스트 추가가 많은 Issue |

> 짝: A팀(강주원·이은규), B팀(정재헌·조수빈). 역할에 따라 Issue의 성격이 다를 뿐, 모두 **화면 하나를 처음부터 끝까지** 맡는다.

### 1.3 두 가지 작업 영역: 기반 작업과 기능 작업

기능 하나를 만드는 일은 **두 영역**으로 나뉜다. 순서대로 넘겨주는 "단계"가 아니라, 담당과 다루는 파일이 다른 "영역"이다.

| | **기반 작업** | **기능 작업** |
|---|---|---|
| 담당 | 리드 | 팀원 |
| 한마디로 | 팀원이 만들 수 있게 **판을 까는 일** | 그 판 위에서 **화면 하나를 끝까지 완성하는 일** |
| 내용 | 허용·거부 정리, DB 테이블, 권한(RLS), 서버 함수와 타입, 빈 화면 경로, 공용 부품 | 화면 만들기, 데이터 연결, 화면 상태 4가지(로딩·빈 목록·오류·권한 없음), 직접 확인 |
| 결과물 | Migration · DB 테스트 · Issue 본문의 "준비된 것" | PR 하나 (Issue 하나) |
| 다루는 파일 | `supabase/`, 공용 파일 | Issue에 적힌 경로의 파일만 |
| 끝났다는 기준 | CI 통과 + Issue에 준비된 것 기재 | 리뷰 체크리스트 8개 통과 |

**검증은 따로 하는 일이 아니다.** 기능 작업의 완료 기준과 리뷰 체크리스트(3.3절)에 들어 있다.

**같은 기능 안에서는 기반이 먼저다. 하지만 팀 전체로 보면 두 영역은 항상 동시에 돌아간다.** 리드가 한 주 앞서 가기 때문이다.

```text
          1주차        2주차        3주차
리드      기반 A   →   기반 B   →   기반 C
팀원                   기능 A   →   기능 B
```

### 1.4 주간 리듬

리드는 항상 **다음 주 기능의 기반 작업**을, 팀원은 **이번 주 기능 작업**을 한다. 리드가 판을 깔면 팀원이 그 위에서 화면을 완성하고, 그동안 리드는 다음 판을 깐다.

| 요일 | 팀원 | 리드 |
|---|---|---|
| **목** (모임) | 지난주 결과 시연 · 이번 주 Issue 받기 | Issue 배정 · 막힌 부분 같이 해결 |
| 금 – 월 | 기능 작업 (막히면 바로 질문) | 다음 주 기능의 기반 작업 |
| **화 23:59** | **PR 마감** | |
| **수** | 상호 리뷰 → 지적 사항 수정 | 최종 리뷰 → 순서대로 Merge |
| 수 밤 | | 운영 배포 확인 · 다음 주 Issue 작성 |

### 1.5 동시에 일해도 충돌하지 않게 Issue를 나누는 규칙

1. **Issue마다 "수정 가능한 파일"을 적는다.** 예: `src/app/tasks/[taskId]/**`만 수정.
2. **공용 파일은 리드만 고친다.**
   - `supabase/**`
   - `package.json` · `package-lock.json`
   - `src/app/layout.tsx` · 내비게이션
   - `src/app/globals.css`
   - `src/lib/supabase/**` · `database.types.ts`
   - `src/components/ui/**` (공용 부품)
3. **화면은 경로 단위로 나눈다.** 예: 목록 `/tasks` · 상세 `/tasks/[taskId]` · 생성 `/tasks/new`를 서로 다른 사람에게.
4. **공용 부품은 리드가 먼저 만든다.** 버튼, 입력칸, 빈 목록·오류·권한 없음 화면 등. 팀원은 가져다 쓴다.
5. **패키지(라이브러리) 추가는 리드에게 요청한다.** AI가 임의로 설치하지 않게 한다.
6. 공용 파일을 꼭 바꿔야 하면 **Issue 댓글로 리드에게 요청**한다. 직접 고치지 않는다.

**초기 실습 Issue의 범위 (10/29 확정):** #1은 `src/app/page.tsx`만, #2는 `src/app/login/**`만 수정한다. `layout.tsx`의 언어 설정·사이트 제목은 리드가 처리한다. 예외로 #3은 새 `supabase/tests/positions_test.sql`만, #4는 새 `supabase/tests/terms_test.sql`만 추가할 수 있다. Migration·RLS·기존 공용 테스트 변경까지 허용하지 않는다. DB 테스트도 다른 팀의 담당자 → 리드 순서로 리뷰한다. 네 Issue는 파일이 겹치지 않아 동시에 시작한다. 저장소의 `GitHub_Issue_초기_정리안.md`를 참고한다.

### 1.6 합치는 방식: 동시에 개발, 수요일에 순서대로 Merge

모든 PR을 한꺼번에 합치지 않는다. 한꺼번에 합치면 합쳐진 상태로는 검사(CI)가 한 번도 돌지 않아, 무엇이 깨뜨렸는지 찾기 어렵다.

1. 다른 PR에 영향이 적은 것부터 하나 Merge한다.
2. 나머지 PR은 **Update branch** 버튼으로 최신 `main`을 반영한다. 검사가 다시 돈다.
3. 초록색이면 다음 PR을 Merge한다.
4. 충돌이 나면 그 PR 작성자가 해결한다 (6.10절). 어려우면 리드와 같이 한다.

1.5의 규칙을 지켰다면 충돌은 거의 나지 않는다.

## 2. Git 규칙: 브랜치 · 커밋 · PR

### 2.1 브랜치

| 규칙 | 내용 |
|---|---|
| 오래 유지하는 브랜치 | **`main` 하나뿐.** `dev` 브랜치는 두지 않는다. (PR마다 생기는 Preview 배포가 개발 서버 역할을 한다) |
| 작업 브랜치 | **Issue 하나에 브랜치 하나.** 항상 최신 `main`에서 만든다. |
| 이름 | `<종류>/<이슈번호>-<짧은-영어-설명>` |
| 예시 | `feat/12-task-list` · `fix/18-login-error` · `test/7-positions-deny` |
| 만드는 법 | Issue 화면 → **Development → Create a branch** (Issue와 자동 연결) |
| 수명 | 최대 1주. Merge되면 삭제된다. |
| 금지 | `main`에 직접 push (브랜치 보호로 막혀 있다) |

### 2.2 커밋 메시지

```
<종류>(<영역>): <무엇을 했는지, 한국어> (#이슈번호)
```

| 종류 | 언제 | 예시 |
|---|---|---|
| `feat` | 새 기능 | `feat(tasks): 업무 목록 화면 추가 (#12)` |
| `fix` | 버그 수정 | `fix(auth): 로그인 오류 문구 수정 (#18)` |
| `test` | 테스트 | `test(db): 직책 중복 거부 테스트 추가 (#7)` |
| `docs` | 문서 | `docs: README 설치 안내 보강 (#20)` |
| `refactor` | 동작은 같고 코드 정리 | `refactor(tasks): 목록 필터 함수 분리 (#12)` |
| `chore` | 설정·패키지 | `chore: Vitest 설정 추가` |

**영역**은 기능 이름이다: `tasks`, `events`, `meetings`, `suggestions`, `auth`, `db`, `ui`, `ci`.

브랜치 안의 커밋은 조금 지저분해도 괜찮다. Merge할 때 **Squash merge**로 PR 하나가 커밋 하나로 합쳐지기 때문이다. 대신 **PR 제목은 반드시 위 형식**으로 쓴다. PR 제목이 그대로 `main`의 커밋 메시지가 된다.

### 2.3 Pull Request

| 규칙 | 내용 |
|---|---|
| 제목 | 커밋 메시지 형식과 같다. 예: `feat(tasks): 업무 목록 화면 추가 (#12)` |
| 본문 첫 줄 | `Closes #12` → Merge되면 Issue가 자동으로 닫힌다 |
| 본문 | PR 템플릿(7.2절)을 채운다 |
| 올리기 전 | `npm run lint` · `npm run typecheck` · `npm test` · `npm run build` 통과 |
| 작업 중 공유 | 끝나기 전이라도 **Draft PR**로 올려 두면 진행 상황을 보여 줄 수 있다 |
| 리뷰어 | 다른 팀의 같은 역할 1명 (3.2절) |
| 크기 | 리뷰어가 15분 안에 볼 수 있는 크기. 너무 크면 Issue를 나눠 달라고 리드에게 요청한다 |
| Merge | 리드만 한다. **Squash and merge**를 쓴다 |

### 2.4 하루 작업 흐름 (명령어)

```bash
# 1. 시작: 최신 main 받기
git switch main
git pull

# 2. 브랜치로 이동 (Issue 화면에서 만들었다면)
git fetch origin
git switch feat/12-task-list

# 3. 작업 후 저장
git add <바꾼 파일>
git commit -m "feat(tasks): 업무 목록 화면 추가 (#12)"

# 4. GitHub에 올리기
git push -u origin feat/12-task-list   # 처음 한 번, 이후엔 git push
```

Fork 앱을 쓰면 같은 일을 버튼으로 한다. Fork에서는 왼쪽 브랜치 목록 → 더블클릭으로 이동 → 아래 커밋 창에 메시지 입력 → **Commit** → 위 **Push** 순서다.

## 3. 리뷰 규칙과 체크리스트

### 3.1 리뷰 단계

| 단계 | 누가 | 무엇을 | 걸리는 시간 |
|---|---|---|---|
| 0 | 작성자 | AI에게 **"이 변경을 리뷰해 줘"**를 먼저 시키고 지적을 반영한다 | 10분 |
| 1 | 다른 팀원 | 체크리스트(3.3절)로 점검하고 **Preview에서 직접 눌러 본다** | 15–20분 |
| 2 | 리드 | 보안 · 범위 · 설명 가능성 위주 최종 확인 → 승인 → Merge | 10분 |

리드의 승인 없이는 Merge되지 않는다 (CODEOWNERS + 브랜치 보호, 6.11절).

**리드 본인 PR (10/29 결정):** GitHub는 작성자 본인의 승인을 허용하지 않아 리드 PR은 Code Owner 승인을 받을 수 없다. 그래서 리드 PR은 다음 순서로 합친다.

1. 1단계 리뷰어(이은규 또는 조수빈)가 체크리스트와 Preview로 확인하고 PR에 **Approve**를 남긴다.
2. CI(`app`·`db`)가 초록색인지 확인한다.
3. 리드가 Merge 화면에서 **"Merge without waiting for requirements to be met"**(관리자 우회)를 체크하고 Squash merge한다.

관리자 우회는 **리드 본인 PR에만** 쓴다. 팀원 PR은 반드시 리드 승인을 받아 합친다.

### 3.2 누가 누구를 리뷰하나

| 변경 | 1단계 리뷰어 |
|---|---|
| 화면 | 강주원 ↔ 정재헌 |
| 데이터 연결 · 테스트 | 이은규 ↔ 조수빈 |
| `supabase/` · CI · 공용 파일 (리드 작업) | 이은규 또는 조수빈 (학습 겸 확인) |

**같은 짝끼리는 리뷰하지 않는다.** 다른 팀의 코드를 읽으면 서로 무엇을 만드는지 자연스럽게 알게 된다.

### 3.3 리뷰 체크리스트

PR에 아래를 복사해 두고 리뷰어가 체크한다.

```markdown
### 리뷰 체크리스트
- [ ] 완료 기준: Issue의 완료 기준을 Preview에서 직접 해 봤다
- [ ] 화면 상태: 로딩 · 빈 목록 · 오류 · 권한 없음이 모두 있다
- [ ] 권한: 권한 없는 계정으로 주소를 직접 입력해도 막힌다
- [ ] 보안: 키 · 비밀번호 · 실제 학생 정보 · service_role이 없다
- [ ] 범위: Issue에 허락된 파일만 바뀌었고, 패키지가 추가되지 않았다
- [ ] 정리: 쓰지 않는 코드 · 의미 없는 주석 · 엉뚱한 파일이 없다
- [ ] 접근성: 키보드만으로 조작되고, 휴대폰 폭(375px)에서 깨지지 않는다
- [ ] 설명: 작성자에게 "이 부분은 왜 이렇게 했나요?"를 하나 물어봤고 답을 들었다
```

### 3.4 리뷰 댓글 쓰는 법

- **무엇이 문제인지 + 어떻게 하면 좋은지**를 같이 쓴다.
  - 나쁜 예: "이상해요"
  - 좋은 예: "목록이 비었을 때 아무것도 안 보여요. `EmptyState` 컴포넌트를 쓰면 될 것 같아요."
- 꼭 고쳐야 하는 것과 의견을 구분한다. 의견에는 앞에 `(선택)`을 붙인다.
- 한 줄 수정이면 **Suggest changes** 기능을 쓴다 (6.8절).

## 4. 막혔을 때

1. **30분 넘게 혼자 붙잡지 않는다.**
2. Issue에 댓글을 쓰고 `blocked` 라벨을 붙인다. 단톡에 Issue 링크를 올린다.
3. 질문 양식:

```text
무엇을 하려고 했나:
무엇을 했나 (명령·AI에게 준 요청):
무엇이 보였나 (오류 메시지 · 캡처, 키·개인정보는 가리기):
기대한 결과:
```

4. 리드나 다른 팀원이 답하면 `blocked`를 뗀다.
5. 공용 파일이나 DB를 바꿔야 풀리는 문제면 리드에게 넘긴다. 직접 고치지 않는다.

## 5. AI 프롬프트 작성 원칙

### 5.1 목표

전공자처럼 쓰라는 건 **어려운 말로 길게 쓰라는 게 아니다.** AI가 헤매지 않고 한 번에 맞게 일하도록 **AI가 스스로 알 수 없는 것만 정확히 알려 주는 것**이다. 필요 없는 정보는 오히려 AI를 헷갈리게 하고 시간을 쓴다.

### 5.2 AI가 이미 아는 것 — 다시 쓰지 않는다

저장소의 `AGENTS.md`(Codex)와 `CLAUDE.md`(Claude Code)에 프로젝트 규칙이 들어 있고, AI가 작업을 시작할 때 자동으로 읽는다.

- 기술 스택 (Next.js 16 · Supabase · Tailwind)
- 금지 사항 (RLS 우회 · 키 사용 · 실제 개인정보 · 테스트 삭제)
- 공용 파일 목록 · 검사 명령 · 화면 상태 4가지 규칙

이 내용을 매번 프롬프트에 붙여 넣지 않는다.

### 5.3 AI가 모르는 것 — 이것만 쓴다

| 항목 | 질문 | 예시 |
|---|---|---|
| **목표** | 무엇이 되면 끝인가 | "국원이 자기 업무 목록을 마감일 순으로 볼 수 있다" |
| **위치** | 어느 파일에서 하나 | "`src/app/tasks/page.tsx`" |
| **재료** | 이미 있는 무엇을 쓰나 | "`tasks` 테이블, `EmptyState` 컴포넌트" |
| **경계** | 이번에 하지 말 것 (Issue에 있을 때만) | "필터 기능은 다음 Issue" |
| **확인** | 어떻게 확인하나 | "빈 목록·오류 상태를 Preview에서 확인" |

다섯 칸을 다 채울 필요는 없다. **대부분은 Issue 본문에 이미 있으므로, Issue를 그대로 주고 한두 줄만 덧붙이면 된다.**

### 5.4 좋은 프롬프트 예시

**처음 시작할 때 (Issue를 그대로 활용)**

```text
Issue #12를 구현해 줘. (Issue 본문 붙여 넣기)
먼저 어떤 파일을 어떻게 바꿀지 계획만 보여 주고, 내가 확인하면 그때 코드를 써 줘.
```

**짧고 정확한 수정 요청**

```text
src/app/tasks/page.tsx에서 목록이 비었을 때 EmptyState 컴포넌트를 보여 줘.
문구는 "아직 배정된 업무가 없습니다".
```

**오류를 고칠 때**

```text
npm run typecheck에서 아래 오류가 나. 원인을 먼저 설명하고 고쳐 줘.
(오류 메시지 그대로 붙여 넣기)
```

**이해가 안 될 때**

```text
방금 만든 코드에서 Suspense를 왜 썼는지 웹 개발 초보자에게 설명해 줘.
```

### 5.5 피해야 할 프롬프트

| 피할 것 | 이유 | 대신 |
|---|---|---|
| "업무 기능 다 만들어 줘" | 범위가 없어 AI가 DB·공용 파일까지 건드린다 | Issue 하나 단위로 요청 |
| 프로젝트 규칙·기획서 전체를 매번 붙여 넣기 | 이미 `AGENTS.md`에 있고, 중요한 정보가 묻힌다 | 이번 작업에 필요한 부분만 |
| 한 프롬프트에 세 가지 일 | 하나가 틀리면 전부 다시 해야 한다 | 한 번에 하나, 확인하고 다음 |
| "안 돼요" | AI가 무엇이 안 되는지 모른다 | 오류 메시지·기대 결과를 그대로 |
| 결과를 확인하지 않고 다음 요청 | 잘못된 코드 위에 계속 쌓인다 | 화면·검사 명령으로 확인 후 다음 |

### 5.6 효율적인 작업 순서

1. **계획 먼저:** "어떤 파일을 어떻게 바꿀지 먼저 보여 줘" → 범위를 벗어나면 이 단계에서 바로잡는다.
2. **구현:** 계획을 승인하고 코드를 쓰게 한다.
3. **확인:** 화면을 직접 보고, 검사 명령을 돌린다.
4. **설명 듣기:** 모르는 부분은 "왜 이렇게 했어?"라고 묻는다. 리뷰에서 설명할 수 있어야 한다.
5. **AI 리뷰:** PR 올리기 전에 "이 변경을 리뷰해 줘"를 시킨다.

### 5.7 AI에 절대 넣지 않는 것

- `.env.local` 내용, Secret key, DB 비밀번호, OAuth Client Secret
- 실제 학생 이름 · 이메일 · 학번 · 건의 원문
- 비밀 값이 보이는 화면 캡처 (가리고 넣는다)

필요하면 **가짜 데이터로 같은 상황을 만들어서** 물어본다.

### 5.8 "전공자처럼" 쓰기 위해 공부할 것

프롬프트의 정확도는 **단어**에서 나온다. "목록 화면"보다 "Server Component에서 조회하고 Suspense로 감싼 목록"이 AI에게 훨씬 정확하다. 강의는 이런 단어를 익히는 것을 목표로 한다.

| 알아야 할 단어 | 쓰이는 곳 | 강의 |
|---|---|---|
| 브랜치 · 커밋 · PR · 충돌 | 모든 작업 | GitHub (이 문서 6장) |
| 페이지 경로 · Server/Client Component · Suspense | 화면 위치와 동작 지정 | Next.js |
| 컴포넌트 · props · state · 폼 · 화면 상태 4가지 | 화면 구성 | React UI |
| 테이블 · 조회(select) · 저장(insert) · RPC | 데이터 연결 | Supabase |
| 로그인 · Role · RLS | "왜 이 데이터가 안 보이지?" 판단 | 인증·권한 |
| 콘솔 · 네트워크 탭 · 오류 메시지 · 테스트 | 문제 찾기 | 디버깅 |

## 6. GitHub 강의

> 목표: 이 장을 읽고 나면 **Issue를 받아 → 브랜치를 만들고 → 커밋·push하고 → PR을 올리고 → 리뷰를 주고받는 것**을 혼자 할 수 있다.

### 6.1 Git과 GitHub

| | Git | GitHub |
|---|---|---|
| 무엇 | 내 컴퓨터에서 파일 변경 이력을 기록하는 프로그램 | Git 저장소를 인터넷에 올려 팀이 함께 쓰는 서비스 |
| 비유 | 게임의 세이브 파일 | 세이브 파일을 공유하는 클라우드 + 단톡 |
| 우리가 쓰는 것 | 터미널 명령 또는 Fork 앱 | 웹사이트 (Issue · PR · 리뷰 · Actions) |

**기본 단어**

| 단어 | 뜻 |
|---|---|
| 저장소 (Repository) | 프로젝트 폴더 전체와 그 변경 이력. 우리 것은 `council-platform` |
| clone | GitHub의 저장소를 내 컴퓨터로 처음 복사하기 |
| pull | GitHub의 최신 변경을 내 컴퓨터로 받기 |
| commit | 내 컴퓨터에서 변경 하나를 기록하기 |
| push | 내 커밋을 GitHub에 올리기 |
| 원격 (origin) | GitHub에 있는 저장소를 부르는 이름 |

**팀원이 알아야 할 것:** commit은 내 컴퓨터에만 저장된다. **push해야 다른 사람이 볼 수 있다.**

### 6.2 Organization (조직)

**무엇인가:** 개인 계정이 아니라 **단체 이름으로 저장소를 소유**하는 공간이다.

**우리 조직:** `INFOSYS-COUNCIL` (https://github.com/INFOSYS-COUNCIL)

**왜 쓰나:**
- 저장소의 주인이 특정 개인이 아니라 학생회다. 기수가 바뀌어도 사람만 바꾸면 된다.
- 권한을 사람마다가 아니라 팀 단위로 줄 수 있다.

**조직 안의 역할**

| 역할 | 누구 | 할 수 있는 것 |
|---|---|---|
| Owner | `gaon2027`(공용 계정), `hkg109`(한지석) | 조직·저장소 설정, 멤버 관리, 브랜치 보호 |
| Member | 팀원 4명 | 조직의 저장소를 보고, 팀을 통해 받은 권한만큼 작업 |

조직의 기본 권한(Base role)은 **Read**다. 조직에 들어온 것만으로는 코드를 올릴 수 없고, 6.3절의 팀을 통해 쓰기 권한을 받는다.

**팀원이 알아야 할 것**
- 초대 메일을 **수락해야** 멤버가 된다 (완료).
- 조직 설정은 바꾸지 않는다. 바꿀 수도 없다.
- 기수가 바뀌면 리드가 새 사람을 초대하고 졸업생을 내보낸다.

### 6.3 Teams (팀)

**무엇인가:** 조직 안의 사람 묶음이다. 묶음 단위로 저장소 권한을 주고, 한 번에 부르거나(@멘션) 리뷰를 요청한다.

**우리 팀:** `@INFOSYS-COUNCIL/developers` (리드 + 팀원 4명)

| 쓰임 | 설명 |
|---|---|
| 권한 | `developers` 팀에 `council-platform` **Write** 권한을 줬다. 팀에 들어가면 자동으로 쓰기 권한이 생긴다 |
| 멘션 | Issue·PR 댓글에 `@INFOSYS-COUNCIL/developers`라고 쓰면 팀 전체에 알림이 간다 |
| 리뷰 요청 | PR의 Reviewers에 사람 대신 팀을 지정할 수도 있다 |
| CODEOWNERS | 특정 폴더의 리뷰 담당을 팀이나 사람으로 지정한다 (6.11절) |

**팀원이 알아야 할 것**
- 팀 멘션은 모두에게 알림이 가니 **꼭 필요할 때만** 쓴다. 보통은 한 사람을 `@아이디`로 부른다.
- 팀원 아이디: `@hkg109` 한지석 · `@joowon0130` 강주원 · `@elee7coder` 이은규 · `@jaehjung0102` 정재헌 · `@goms1107` 조수빈

### 6.4 저장소 권한 단계

| 권한 | 할 수 있는 것 | 우리 |
|---|---|---|
| Read | 보기, Issue·PR에 댓글 | 조직 기본값 |
| Triage | + Issue·PR 라벨·담당자 관리 | 쓰지 않음 |
| **Write** | + 브랜치 만들기, push, PR 만들기, 리뷰 | **팀원 (developers 팀)** |
| Maintain | + 저장소 일부 설정 | 쓰지 않음 |
| Admin | + 모든 설정, 저장소 삭제 | Owner (리드·공용 계정) |

**팀원이 알아야 할 것:** Write 권한이 있어도 **`main`에는 직접 push할 수 없다.** 브랜치 보호(6.11절)가 막는다. 반드시 PR을 거친다.

### 6.5 Issues (이슈)

**무엇인가:** 할 일 · 버그 · 질문 하나를 기록하는 카드다. 우리에게는 **작업 지시서이자 AI에게 줄 설명서**다.

**Issue의 구성**

| 칸 | 뜻 | 우리 규칙 |
|---|---|---|
| 제목 | 무엇을 하는가 | 동사로 끝나게. 예: "업무 목록 화면 만들기" |
| 본문 | 목표 · 수정 가능 파일 · 완료 기준 · 읽을 강의 | Issue 템플릿(7.1절)을 따른다 |
| Assignees | 담당자 | 리드가 지정. 한 Issue에 한 명 |
| Labels | 분류 | 아래 표 |
| Type | 종류 | Task / Bug / Feature |
| Milestone | 마감 묶음 | 주차 단위. 예: "3주차 (11/12)" |
| Development | 연결된 브랜치·PR | 브랜치를 Issue에서 만들면 자동 연결 |

**우리 라벨**

| 라벨 | 뜻 | 언제 붙이나 |
|---|---|---|
| `frontend` | 화면·컴포넌트·스타일 | 영역 |
| `database` | 테이블·Migration·RLS·DB 테스트 | 영역 |
| `auth` | 로그인·권한 (리드 리뷰 필수) | 영역 |
| `infra` | CI·배포·환경 설정 | 영역 |
| `accessibility` | 키보드·스크린리더·명도 대비 | 해당될 때 |
| `documentation` | README·가이드·문서 | 해당될 때 |
| `good first issue` | 처음 해 보기 좋은 작은 작업 | 해당될 때 |
| `blocked` | 막혀서 도움 필요 | 30분 넘게 막히면. 풀리면 뗀다 |
| `needs decision` | 회장단·리드 결정 필요 | 결정이 나면 뗀다 |

**Issue를 닫는 법:** PR 본문에 `Closes #12`라고 쓰면, PR이 `main`에 Merge될 때 Issue #12가 자동으로 닫힌다. `Fixes`, `Resolves`도 같다. 그냥 `#12`만 쓰면 연결만 되고 닫히지는 않는다.

**팀원이 알아야 할 것**
- 내 Issue 찾기: Issues 탭 → **Assigned to me**
- 시작하면 Issue에 "시작합니다" 댓글 → Development에서 브랜치 생성
- 질문·진행 상황은 **Issue 댓글**에 남긴다. 단톡은 링크만. 기록이 Issue에 남아야 다음 사람이 본다
- Issue 본문은 리드가 관리한다. 바꿔야 할 내용이 있으면 댓글로 말한다

### 6.6 Branch (브랜치)

**무엇인가:** `main`에서 갈라져 나온 **내 작업 공간**이다. 내 브랜치에서 무엇을 해도 `main`과 다른 사람의 작업에 영향이 없다.

```text
main ──●────────●────────●──────────  (항상 동작하는 상태)
        \                 ↑ Merge
         ●──●──●──────────┘
         feat/12-task-list  (내 작업)
```

**만드는 법 (추천):** Issue → 오른쪽 **Development** → **Create a branch** → Branch source가 `main`인지 확인 → **Create branch** → 화면에 나오는 명령 실행

```bash
git fetch origin
git switch feat/12-task-list
```

**지금 어느 브랜치인지 확인:** `git status`의 첫 줄, Fork 앱 왼쪽 위, 또는 Starship 프롬프트에 표시된다.

**팀원이 알아야 할 것**
- 작업 전에 **내가 내 브랜치에 있는지** 꼭 확인한다. `main`에서 작업하는 실수가 가장 흔하다.
- 브랜치 하나에는 Issue 하나만. 다른 일이 생기면 새 Issue · 새 브랜치.
- 다른 사람 브랜치에는 push하지 않는다.

### 6.7 Commit · Push

**무엇인가:** commit은 "여기까지 저장"이고, push는 "GitHub에 올리기"다.

```bash
git status                 # 무엇이 바뀌었는지 보기
git add src/app/tasks/     # 저장할 파일 고르기
git commit -m "feat(tasks): 업무 목록 화면 추가 (#12)"
git push                   # 첫 push는 git push -u origin <브랜치>
```

**팀원이 알아야 할 것**
- `git add .`는 모든 파일을 올리므로 **엉뚱한 파일**(`.env.local`, 캡처 이미지 등)이 섞일 수 있다. `git status`로 먼저 확인한다.
- `.env.local`은 `.gitignore`에 있어서 올라가지 않는 게 정상이다.
- 기능이 하나 동작할 때마다 작게 커밋한다. 잘못되면 그 지점으로 돌아갈 수 있다.
- 하루 작업이 끝나면 push해 둔다. 내 컴퓨터가 고장 나도 GitHub에 남는다.

### 6.8 Pull Request (PR)

**무엇인가:** "내 브랜치의 변경을 `main`에 합쳐 주세요"라는 요청이다. 리뷰 · 자동 검사 · 미리보기가 모두 PR에서 일어난다.

**만드는 법**
1. push하면 저장소 화면에 노란 띠 **Compare & pull request**가 뜬다 → 클릭
2. base: `main` ← compare: `내 브랜치` 확인
3. 제목: `feat(tasks): 업무 목록 화면 추가 (#12)`
4. 본문: 템플릿 채우기, 첫 줄 `Closes #12`
5. 오른쪽 Reviewers에 1단계 리뷰어 지정, Labels 지정
6. 아직 작업 중이면 **Create draft pull request**, 다 됐으면 **Create pull request**

**PR 화면의 탭**

| 탭 | 내용 | 볼 것 |
|---|---|---|
| Conversation | 설명 · 댓글 · 검사 결과 · Merge 버튼 | 검사가 모두 초록색인지 |
| Commits | 이 PR의 커밋 목록 | |
| Checks | CI(`app`, `db`) 상세 로그 | 빨간색이면 여기서 원인 확인 |
| Files changed | 바뀐 파일과 줄 | 리뷰는 여기서 한다 |

**Preview 배포:** PR을 만들면 Vercel 봇이 댓글로 **미리보기 주소**를 단다. 리뷰어는 이 주소에서 직접 눌러 본다. (Preview는 개발용 DB `council-dev`에 연결되어 있다)

**리뷰하는 법 (리뷰어)**
1. **Files changed** 탭 → 줄 번호 옆 **+** 를 눌러 그 줄에 댓글
2. 한 줄 수정 제안: 댓글 창의 **±(Suggest changes)** 버튼 → 고친 코드를 쓰면 작성자가 버튼 하나로 반영할 수 있다
3. 다 봤으면 오른쪽 위 **Review changes** →
   - **Comment**: 의견만
   - **Approve**: 통과
   - **Request changes**: 고쳐야 통과

**리뷰를 받으면 (작성자)**
- 지적 사항을 고쳐서 같은 브랜치에 commit · push하면 PR에 자동으로 반영된다. **새 PR을 만들지 않는다.**
- 고친 댓글에는 **Resolve conversation**을 누른다.

**Merge (리드)**
- 조건: 검사 초록색 + 1단계 리뷰 체크 + 리드 승인
- **Squash and merge** → PR 제목이 `main`의 커밋 메시지가 된다
- Merge 후 브랜치는 자동 삭제된다. 팀원은 `git switch main` → `git pull`로 최신 상태를 받고 다음 Issue를 시작한다.

**팀원이 알아야 할 것**
- PR은 **작업 단위**다. 하나에 여러 기능을 섞지 않는다.
- PR을 올렸으면 리뷰어에게 단톡으로 링크를 보낸다.
- Merge는 리드만 한다.

### 6.9 Update branch: 최신 main 반영하기

내가 작업하는 동안 다른 PR이 `main`에 먼저 합쳐질 수 있다. 그러면 내 PR 화면에 **"This branch is out-of-date with the base branch"**가 뜬다.

- PR 화면의 **Update branch** 버튼을 누르면 최신 `main`이 내 브랜치에 합쳐지고 검사가 다시 돈다.
- 그다음 내 컴퓨터에서도 `git pull`을 해서 맞춰 둔다.

### 6.10 충돌 (Conflict)

**무엇인가:** 두 사람이 **같은 파일의 같은 부분**을 다르게 고쳐서, Git이 어느 쪽을 남길지 정하지 못하는 상태다. PR 화면에 **"This branch has conflicts that must be resolved"**가 뜬다.

**충돌 표시의 모양**

```text
<<<<<<< feat/12-task-list   ← 내 변경
<h1>업무 목록</h1>
=======
<h1>내 업무</h1>
>>>>>>> main                ← main에 먼저 들어간 변경
```

**해결하는 법**
1. 내 컴퓨터에서:
   ```bash
   git switch feat/12-task-list
   git pull origin main
   ```
2. 충돌 난 파일을 VS Code로 연다. 위에 **Accept Current / Accept Incoming / Accept Both** 버튼이 보인다.
3. 두 변경의 목적을 생각해서 남길 내용을 고른다. 모르겠으면 AI에게 충돌 부분을 보여 주고 "두 변경의 의도를 살려 합쳐 줘"라고 요청한다.
4. `<<<<<<<`, `=======`, `>>>>>>>` 표시가 남지 않았는지 확인한다.
5. `npm run build`가 되는지 확인 → `git add` → `git commit` → `git push`

**예방:** 1.5절 규칙(파일 나눠 갖기)을 지키고, 작업 시작 전 `git pull`, PR은 일주일 안에 끝낸다.

### 6.11 Actions(CI) · 브랜치 보호 · CODEOWNERS

**GitHub Actions (CI):** PR을 올리거나 push할 때 자동으로 검사가 돈다.

| 검사 | 하는 일 | 빨간색이면 |
|---|---|---|
| `app` | lint → typecheck → 단위 테스트 → build | Checks 탭에서 실패한 단계의 오류 메시지를 확인 → 내 컴퓨터에서 같은 명령으로 재현 |
| `db` | 새 DB에 Migration 적용 → pgTAP 권한 테스트 | 보통 리드 영역. 테스트를 추가했다면 내 테스트 확인 |

**브랜치 보호 (Branch protection):** `main`을 지키는 규칙이다.
- `main`에 직접 push 금지 → 반드시 PR
- 검사(`app`, `db`)가 초록색이어야 Merge 가능
- 리뷰 승인이 있어야 Merge 가능
- 해결되지 않은 리뷰 댓글이 있으면 Merge 불가
- 최신 `main`을 반영한 상태로 검사가 다시 통과해야 Merge 가능 (Update branch 버튼)
- force push · 브랜치 삭제 금지
- 관리자(리드)는 우회할 수 있지만 리드 본인 PR에만 쓴다 (3.1절)

**Preview:** PR마다 Vercel 봇이 댓글로 Preview 주소를 단다. Preview는 로그인 없이 누구나 열 수 있다(10/29 보호 해제). dev DB와 가짜 데이터를 쓰므로 실제 학생 정보를 넣지 않는다.

**CODEOWNERS:** `.github/CODEOWNERS` 파일에 "이 폴더는 이 사람이 승인해야 한다"를 적어 둔다. 우리는 **모든 파일에 리드 승인**이 필요하도록 설정한다. 그래서 1단계 리뷰를 받아도 리드 승인 전에는 Merge되지 않는다.

**팀원이 알아야 할 것:** 검사가 빨간색이면 리뷰를 요청하기 전에 먼저 고친다. 오류 메시지를 AI에게 그대로 주면 대부분 바로 해결된다.

### 6.12 Milestones · 알림

**Milestone:** 마감일이 있는 Issue 묶음이다. 우리는 **주차 단위**로 만든다 (예: "3주차 (11/12)"). Milestones 탭에서 이번 주 진행률을 막대로 볼 수 있다.

**알림:** 리뷰 요청 · 멘션 · 내 Issue 댓글은 GitHub 알림(오른쪽 위 종 모양)과 이메일로 온다.
- 이메일이 너무 많으면: 프로필 → Settings → Notifications에서 조절
- 최소한 **"리뷰 요청"과 "멘션"**은 켜 둔다

### 6.13 자주 하는 실수와 해결

| 상황 | 해결 |
|---|---|
| `main`에서 작업하고 커밋까지 했다 | push하기 전이면 `git switch -c feat/12-task-list` → 지금 변경이 새 브랜치로 옮겨진다. 리드에게 알린다 |
| push가 거절됐다 (`rejected`) | `git pull` 후 다시 `git push` |
| `main`에 push하려다 막혔다 | 정상이다. 브랜치를 만들어 PR로 올린다 |
| 커밋 메시지를 잘못 썼다 | 괜찮다. Squash merge할 때 PR 제목이 쓰인다. PR 제목만 맞게 고친다 |
| 엉뚱한 파일을 커밋했다 | 다음 커밋에서 되돌리고 PR에 적는다. 키·개인정보라면 **즉시 리드에게 알린다** (키 폐기·재발급) |
| 브랜치가 너무 오래돼 충돌이 많다 | 리드와 상의. 새 브랜치에서 다시 하는 게 빠를 때가 많다 |
| 무엇이 바뀌었는지 모르겠다 | `git status`, `git diff`, 또는 Fork 앱에서 확인 |
